## Before you begin

## Why this decision matters

Start by distinguishing a deterministic workflow from an agent. A workflow follows steps you specify; an agent chooses its next action from observations. That choice introduces failure modes: loops, wrong tools, unsupported answers, and actions outside the user’s authority. A useful first system needs a task boundary before a model.

Your capstone helps a support representative answer questions from synthetic business policies. Its first release is read-only. The success criterion is evidence-backed answers or a clear inability to answer, not a fluent response on every input. Measure current human effort before claiming improvement. Keep scope small enough that you can inspect every failure.

## Vocabulary used in this session

### Workflow

Application code defines the sequence and decision gates.

### Agent

The system chooses a next action from observations within application-enforced limits.

### Task boundary

The explicit user, input, output and actions excluded from the release.

## Worked implementation: From prompts to useful systems

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
def handle(requested):
    allowed = {'read_policy', 'draft'}
    return {'permitted': sorted(set(requested) & allowed),
            'review': sorted(set(requested) - allowed)}
result = handle(['read_policy', 'draft', 'refund'])
assert result == {'permitted': ['draft', 'read_policy'], 'review': ['refund']}
print(result)
```

## Expected observation

```text
{'permitted': ['draft', 'read_policy'], 'review': ['refund']}
```

## Walk through the mechanism and its limits

The requested operations are proposals. Intersection with a fixed application allowlist determines permitted operations; the difference is routed to review. No code here issues a refund. This is a scope baseline, not a natural-language intent detector. A real dispatcher must repeat authorization when an operation executes.
