## Before you begin

## Why this decision matters

Start by distinguishing a deterministic workflow from an agent. A workflow follows steps you specify; an agent chooses its next action from observations. That choice introduces failure modes: loops, wrong tools, unsupported answers, and actions outside the user’s authority. A useful first system needs a task boundary before a model.

Your capstone helps a support representative answer questions from synthetic business policies. Its first release is read-only. The success criterion is evidence-backed answers or a clear inability to answer, not a fluent response on every input. Measure current human effort before claiming improvement. Keep scope small enough that you can inspect every failure.

## Vocabulary used in this session

### Workflow

Application code defines the sequence and decision gates.

### Agent

The system chooses a next action from observations within application-enforced limits.

### Task boundary

The explicit user, input, output and actions excluded from the release.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Workflow

A workflow makes the next step explicit in code: receive a question, select authorized policy, draft, then request review. Start by tracing one request through that sequence. This makes failures attributable to a stage. Use it as the baseline before adding model-selected actions; a longer reasoning trace does not itself make the task work better.

## Step 2 · Agent

An agent selects its next action from observations. The application must still enforce the set of permitted actions, the available evidence and a stopping rule. Here requested operations are manually supplied proposals, not language understanding. Intersecting them with an allowlist permits reading and drafting; it cannot grant authority to refund money.

## Step 3 · Task boundary

A task boundary names the user, source, output and excluded effects. For this fixture, preparing a source-linked draft is allowed but changing an account is excluded. Permission to draft also does not supply missing evidence: no policy must produce an unavailable result. These two independent checks prevent a permitted operation from manufacturing an unsupported answer.

## Walk through the data and decision

1. handle separates permitted operations from review proposals using set intersection and difference.

2. refund appears only in review; no function implements that effect.

3. Adding a source check must happen before draft text is constructed.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
def handle(requested):
    allowed = {'read_policy', 'draft'}
    return {'permitted': sorted(set(requested) & allowed),
            'review': sorted(set(requested) - allowed)}
result = handle(['read_policy', 'draft', 'refund'])
assert result == {'permitted': ['draft', 'read_policy'], 'review': ['refund']}
print(result)
```

## Walk through the mechanism and its limits

The requested operations are proposals. Intersection with a fixed application allowlist determines permitted operations; the difference is routed to review. No code here issues a refund. This is a scope baseline, not a natural-language intent detector. A real dispatcher must repeat authorization when an operation executes.

## Production evidence

A notebook or chat demo is an early prototype. Completion requires operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to A read-only assistant over three synthetic policies

### Latency vs. Cost vs. Quality

Compare a fixed workflow and a bounded agent on identical labeled cases. Count failed attempts and review time in cost per accepted result; retain p50/p95 and a quality floor.

### Deterministic Evaluation

Version a case set containing supported, ambiguous, missing-source and unauthorized inputs. Schema, permissions and stop conditions are executable assertions; label semantic support separately.

### Context Management

Record instruction, tool-schema, history, evidence and output allocations. Preserve source IDs and exceptions; label estimates separately from provider usage.

## Failure and deployment work

Reject oversized input, preserve it on provider failure, and cap attempts, elapsed time and concurrent work.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
