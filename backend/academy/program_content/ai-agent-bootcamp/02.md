# A reproducible Python workspace

## Understand the decision: A reproducible Python workspace

## Before you begin

Complete sessions 1–1 in this bootcamp. Keep your policy fixtures and evaluation labels in your own workspace. The example below runs independently so a prior missing file cannot block understanding.

## Why this decision matters

Reproducibility means someone else can run the same exercise without your editor state, global packages, or private files. Separate the academy application from the capstone workspace. Use a virtual environment, a declared interpreter version, and a README with exact commands. Begin with standard-library code so a provider outage cannot block basic engineering practice.

Understand the difference between an environment variable and a secret committed into a file. A `.env.example` documents variable names and fake values; an actual credential never belongs in a fixture, a screenshot, or learner notes. A reproducible setup should fail clearly when required configuration is absent.

## Vocabulary used in this session

### Virtual environment

An isolated Python interpreter environment with its own installed dependencies.

### Reproducibility

Another person can run the project from declared files and setup steps.

### Secret boundary

Credentials remain outside tracked code, fixtures, logs and learner notes.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Virtual environment

A virtual environment separates the project interpreter and dependencies from other projects. Create it, invoke its Python explicitly, and record the version. Merely naming a folder .venv does not isolate anything. This lesson’s standard-library example needs no packages, but later dependencies belong in a declared file rather than undocumented global installs.

## Step 2 · Reproducibility

Reproducibility starts with paths and setup assumptions. Path(__file__) identifies the executing module; Path.cwd() identifies where its caller started. The baseline creates a miniature project and calls its loader from two directories. Both must resolve the same fixture. A missing required file should become a clear setup error, not silent empty data.

## Step 3 · Secret boundary

A secret boundary controls what enters tracked files, fixtures, logs and notes. A .gitignore can prevent a new credential file from being added accidentally; it does not remove an already tracked secret or sanitize logs. Use synthetic configuration in the exercise, list required environment variable names, and check the actual tracked files before sharing.

## Worked implementation: A reproducible Python workspace

## Walk through the data and decision

1. The temporary root contains app/loader.py and data/policies.json.

2. The loader climbs from its own file to the root, so changing cwd does not change data.

3. finally restores the original cwd before temporary-directory cleanup.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import json, os
with TemporaryDirectory() as folder:
    root = Path(folder)
    (root / 'app').mkdir()
    (root / 'data').mkdir()
    (root / 'data/policies.json').write_text('[{"id":"returns-v1"}]', encoding='utf-8')
    loader = root / 'app/loader.py'
    loader.write_text('from pathlib import Path\nimport json\ndef load():\n    root = Path(__file__).resolve().parent.parent\n    return json.loads((root / "data/policies.json").read_text(encoding="utf-8"))\n', encoding='utf-8')
    import runpy
    original = Path.cwd()
    try:
        os.chdir(root / 'app')
        first = runpy.run_path(str(loader))['load']()
        os.chdir(root.parent)
        second = runpy.run_path(str(loader))['load']()
        assert first == second == [{'id': 'returns-v1'}]
    finally:
        os.chdir(original)
print('two working directories: same fixture')
```

## Walk through the mechanism and its limits

The example creates every required file in a temporary project. The loader resolves its own file location, then ascends to the declared project root. Changing the caller’s working directory therefore does not change the fixture path. finally restores the shell location before the temporary directory is removed. This tests paths; dependency isolation still requires the fresh virtual environment exercise.

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Completion requires operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to A read-only assistant over three synthetic policies

### Latency vs. Cost vs. Quality

Compare a fixed workflow and a bounded agent on identical labeled cases. Count failed attempts and review time in cost per accepted result; retain p50/p95 and a quality floor.

### Deterministic Evaluation

Version a case set containing supported, ambiguous, missing-source and unauthorized inputs. Schema, permissions and stop conditions are executable assertions; label semantic support separately.

### Context Management

Record instruction, tool-schema, history, evidence and output allocations. Preserve source IDs and exceptions; label estimates separately from provider usage.

## Failure and deployment work

Reject oversized input, preserve it on provider failure, and cap attempts, elapsed time and concurrent work.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.

## Module evidence to retain

module-engineering-evidence.json: dataset/release IDs; latency/cost/quality comparison; automated checks and critical failures; context and cache policy; deployment/failure observations. Mark unmeasured fields as not tested.
