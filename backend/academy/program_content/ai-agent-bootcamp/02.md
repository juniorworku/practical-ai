# A reproducible Python workspace

## Understand the decision: A reproducible Python workspace

## Before you begin

Complete sessions 1–1 in this bootcamp. Keep your policy fixtures and evaluation labels in your own workspace. The example below runs independently so a prior missing file cannot block understanding.

## Why this decision matters

Reproducibility means someone else can run the same exercise without your editor state, global packages, or private files. Separate the academy application from the capstone workspace. Use a virtual environment, a declared interpreter version, and a README with exact commands. Begin with standard-library code so a provider outage cannot block basic engineering practice.

Understand the difference between an environment variable and a secret committed into a file. A `.env.example` documents variable names and fake values; an actual credential never belongs in a fixture, a screenshot, or learner notes. A reproducible setup should fail clearly when required configuration is absent.

## Vocabulary used in this session

### Virtual environment

An isolated Python interpreter environment with its own installed dependencies.

### Reproducibility

Another person can run the project from declared files and setup steps.

### Secret boundary

Credentials remain outside tracked code, fixtures, logs and learner notes.

## Worked implementation: A reproducible Python workspace

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import json, os
with TemporaryDirectory() as folder:
    root = Path(folder)
    (root / 'app').mkdir()
    (root / 'data').mkdir()
    (root / 'data/policies.json').write_text('[{"id":"returns-v1"}]', encoding='utf-8')
    loader = root / 'app/loader.py'
    loader.write_text('from pathlib import Path\nimport json\ndef load():\n    root = Path(__file__).resolve().parent.parent\n    return json.loads((root / "data/policies.json").read_text(encoding="utf-8"))\n', encoding='utf-8')
    import runpy
    original = Path.cwd()
    try:
        os.chdir(root / 'app')
        first = runpy.run_path(str(loader))['load']()
        os.chdir(root.parent)
        second = runpy.run_path(str(loader))['load']()
        assert first == second == [{'id': 'returns-v1'}]
    finally:
        os.chdir(original)
print('two working directories: same fixture')
```

## Expected observation

```text
two working directories: same fixture
```

## Walk through the mechanism and its limits

The example creates every required file in a temporary project. The loader resolves its own file location, then ascends to the declared project root. Changing the caller’s working directory therefore does not change the fixture path. finally restores the shell location before the temporary directory is removed. This tests paths; dependency isolation still requires the fresh virtual environment exercise.

## Build it yourself

1. Create `app`, `tests`, `data`, and `docs` folders in a new capstone directory.
2. Add a smoke test that imports your own module and checks a deterministic function.
3. Write setup instructions for your operating system and test them from a fresh shell.
4. Add `.gitignore` entries for environments, credentials, caches, and generated private data.

## Break it deliberately

Run tests from another working directory. If they depend on an accidental relative path or global import, resolve paths from the project root and explain the correction.
