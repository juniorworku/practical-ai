## Understand the decision: Build a small evaluation dataset first

## Before you begin

## Why this decision matters

An evaluation dataset is a set of inputs paired with a behavioral expectation and the evidence supporting that expectation. It turns “seems good” into a repeatable comparison. Keep a development set for iteration and a separate holdout set for a final check. When you inspect a holdout failure and tune to it, it is no longer an untouched holdout example.

For a policy assistant, score source selection, answer correctness, citation support, and abstention separately. A model can quote the right document while drawing the wrong conclusion. A small carefully labeled set is more informative than hundreds of unlabeled prompts. Record ambiguous examples instead of forcing false certainty.

## Vocabulary used in this session

### Evaluation case

An input with an expected behavior and the evidence supporting that expectation.

### Holdout set

Cases reserved for a final comparison and not used to tune the current system.

### Label ambiguity

A case whose expected outcome needs clarification rather than a forced confident label.

## Worked implementation: Build a small evaluation dataset first

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
cases = [
 {'id':'q1','family':'unopened','split':'development','expected':'answer'},
 {'id':'q2','family':'missing_condition','split':'development','expected':'clarify'},
 {'id':'q3','family':'unavailable','split':'holdout','expected':'abstain'},
]
def used_for_tuning(case):
    return dict(case, split='development', reason='inspected and tuned')
cases[2] = used_for_tuning(cases[2])
assert not any(c['split'] == 'holdout' for c in cases)
assert len({c['id'] for c in cases}) == len(cases)
print([(c['id'], c['split'], c['expected']) for c in cases])
```

## Expected observation

```text
[('q1', 'development', 'answer'), ('q2', 'development', 'clarify'), ('q3', 'development', 'abstain')]
```

## Walk through the mechanism and its limits

Each expected label names behavior, not merely a preferred sentence. q2 is answerable after the customer supplies a condition; q3 lacks a policy at all. Relabeling an inspected holdout preserves its history instead of deleting the failure. No score in this example estimates generalization: there is now no untouched set.

## Build and challenge your own version

## Worked example

Use JSON Lines, one independent case per line:

```json
{"id":"returns-01","question":"Can an unopened item be returned after 10 days?","expected_source":"returns-v1","expected":"answer","must_include":["14 days"],"must_not_include":["refund approved"]}
```

A separate case asks about an item after 40 days. Its expected outcome differs even though the vocabulary is similar.

## Build it yourself

1. Create 20 synthetic cases covering normal, ambiguous, missing-evidence, conflicting-policy, and malicious-input scenarios.
2. Annotate each with the expected source and whether the assistant should answer, clarify, or abstain.
3. Split 15 development and five holdout cases before implementing retrieval.
4. Ask another person, or perform a delayed second pass, to check your labels against the policies.

## Break it deliberately

Insert two near-duplicate questions with different dates. A scorer based only on shared words should fail, exposing why string overlap is insufficient.

## Acceptance checks

- Every case has an expected behavior and a supporting policy ID, or an explicit no-source label.
- The split and label revision are recorded.
- At least five cases test behavior beyond a happy-path answer.
