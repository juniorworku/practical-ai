## Understand the decision: Build a small evaluation dataset first

## Before you begin

## Why this decision matters

An evaluation dataset is a set of inputs paired with a behavioral expectation and the evidence supporting that expectation. It turns “seems good” into a repeatable comparison. Keep a development set for iteration and a separate holdout set for a final check. When you inspect a holdout failure and tune to it, it is no longer an untouched holdout example.

For a policy assistant, score source selection, answer correctness, citation support, and abstention separately. A model can quote the right document while drawing the wrong conclusion. A small carefully labeled set is more informative than hundreds of unlabeled prompts. Record ambiguous examples instead of forcing false certainty.

## Vocabulary used in this session

### Evaluation case

An input with an expected behavior and the evidence supporting that expectation.

### Holdout set

Cases reserved for a final comparison and not used to tune the current system.

### Label ambiguity

A case whose expected outcome needs clarification rather than a forced confident label.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Evaluation case

An evaluation case includes actual input, expected behavior and the source or missing condition justifying the label. “Answer” without a policy reference is not enough. Distinguish a missing customer condition, which may be clarified, from unavailable organizational policy, which requires abstention. Record ambiguous labels instead of forcing agreement.

## Step 2 · Holdout set

A holdout remains untouched only while it has not influenced implementation choices. Once you inspect an error and tune against it, move that case to development and record why. Splitting by scenario family reduces leakage from near-identical paraphrases. Fresh holdout cases must contain genuinely different decisions, not new IDs for the same tuned question.

## Step 3 · Label ambiguity

Label ambiguity is a property of evidence and task definition, not a model failure. Ask what fact would decide the case, annotate that missing fact and resolve disagreements against the policy. Expected behavior can legitimately be clarify. Keep the annotation revision so comparisons do not silently change both candidate and answer key.

```python
cases = [
 {'id':'q1','family':'unopened','split':'development','expected':'answer'},
 {'id':'q2','family':'missing_condition','split':'development','expected':'clarify'},
 {'id':'q3','family':'unavailable','split':'holdout','expected':'abstain'},
]
def used_for_tuning(case):
    return dict(case, split='development', reason='inspected and tuned')
cases[2] = used_for_tuning(cases[2])
assert not any(c['split'] == 'holdout' for c in cases)
assert len({c['id'] for c in cases}) == len(cases)
print([(c['id'], c['split'], c['expected']) for c in cases])
```

## Walk through the mechanism and its limits

Each expected label names behavior, not merely a preferred sentence. q2 is answerable after the customer supplies a condition; q3 lacks a policy at all. Relabeling an inspected holdout preserves its history instead of deleting the failure. No score in this example estimates generalization: there is now no untouched set.

A notebook or chat demo is an early prototype. Graduation builds toward operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. ### Latency vs. Cost vs. Quality

### Deterministic Evaluation

## Failure and deployment work

Reject oversized input, preserve it on provider failure, and cap attempts, elapsed time and concurrent work.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
