## Why this decision matters

A prompt is one part of an interface, not an authority boundary. Specify the task, available evidence, uncertainty behavior, and output fields. Treat the response as untrusted data that must be parsed and validated before use. Valid JSON does not establish factual correctness, and a schema cannot prove a cited passage supports a claim.

Keep trusted application instructions separate from retrieved content. An excerpt may contain instructions addressed to a reader; it must remain source data. Record a prompt revision whenever you change intended behavior, then rerun the same evaluation cases. Do not collect hidden reasoning; collect concise decision labels, sources, and observable tool results.

## Vocabulary used in this session

### Output contract

Allowed fields, types, statuses and invariants checked before a response is used.

### Citation integrity

Referenced source IDs must exist in the selected evidence set.

### Factual support

A cited passage must actually establish the answer’s claim.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Output contract

An output contract separates parsing from application use. Parse JSON, require exactly the intended keys, then check types, status values and cross-field rules. Python bool is an int subclass, so exact type checks matter for numeric schemas. Return a structured error before the UI or a tool consumes malformed output.

## Step 2 · Citation integrity

Citation integrity checks identity: every cited ID exists in the selected authorized evidence, with no duplicates. It cannot establish that a passage supports the sentence. A real source ID attached to the opposite policy statement must pass identity checking and still fail support review. Keep those outcomes in separate report fields.

## Step 3 · Factual support

Factual support asks whether each claim follows from the passage and preserves its conditions. The fixture policy allows unopened items within fourteen days; “opened items always qualify” contradicts it. Human-reviewed labels can test the pipeline without pretending a string validator understands meaning. Missing evidence should trigger clarification or abstention according to what is missing.

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
import json
def validate(raw, known):
    try:
        data = json.loads(raw)
    except (ValueError, TypeError):
        return ['invalid_json']
    if type(data) is not dict or set(data) != {'status','answer','citations'}:
        return ['fields']
    if data['status'] not in ('answer','clarify','abstain') or type(data['answer']) is not str:
        return ['types_or_status']
    cites = data['citations']
    if type(cites) is not list or any(type(x) is not str for x in cites):
        return ['citation_type']
    if len(set(cites)) != len(cites) or any(x not in known for x in cites):
        return ['citation_identity']
    if data['status'] == 'answer' and (not cites or not data['answer'].strip()):
        return ['answer_requires_evidence']
    return []
valid = {'status':'answer','answer':'Unopened items within 14 days.','citations':['returns-v1']}
assert validate(json.dumps(valid), {'returns-v1'}) == []
assert validate('{', {'returns-v1'}) == ['invalid_json']
assert validate(json.dumps(dict(valid, citations=['invented'])), {'returns-v1'}) == ['citation_identity']
unsupported = dict(valid, answer='Opened items are always eligible.')
assert validate(json.dumps(unsupported), {'returns-v1'}) == []
print('structure and identity passed; unsupported claim still requires factual review')
```

## Walk through the mechanism and its limits

Parsing, exact keys, types, membership and answer invariants are separate checks with separate failure reasons. The last assertion deliberately passes an unsupported sentence. This proves the limit of validation: reference existence is not evidence that the passage supports a claim. A reviewer or separately evaluated support check must compare the actual wording and policy conditions.

Define a provider-neutral result contract:

```json
{"status":"answer","answer":"Unopened items qualify within 14 days.","citations":["returns-v1"]}
```

Allowed statuses are `answer`, `clarify`, and `abstain`. These are the exact three provider-result fields used by the validator. The application stores human-review state separately; adding a `needs_review` key to this provider payload would violate its exact-field contract. An answer with no citations should be rejected even if every field has the correct type.

### Latency vs. Cost vs. Quality

Measure time to first output and total completion separately. Compare retry cost and accepted-output rate under a fixed overall deadline.

### Deterministic Evaluation

Fake 429, 503, permission failure, malformed JSON, cancellation and a partial stream. Assert bounded retry and no false saved/success status.

### Context Management

Track actual input/output usage when supplied; include retry usage. Key caches by owner, model, prompt and source revisions; never cache partial streams as complete answers.

## Failure and deployment work

Honor Retry-After within the total budget, stop sibling tasks on disconnect, and separate safe draft retries from uncertain external writes.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
