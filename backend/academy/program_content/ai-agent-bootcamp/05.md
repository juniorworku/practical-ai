## Understand the decision: Provider adapters, timeouts, and failures

## Before you begin

## Why this decision matters

Put provider-specific calls behind a narrow interface so the rest of your system receives the same result or a typed failure. Start with a fake provider returning predictable responses. A real provider can later implement the same interface with credentials on the server. Reading lessons should never trigger a paid call.

Distinguish retryable transient failures from invalid requests and permission failures. Bound both attempts and total elapsed time. Retrying every exception hides configuration errors and can increase cost. Log failure categories and request identifiers, not credentials or full private prompts. A fallback to a different provider is a data-routing decision, not an invisible convenience.

## Vocabulary used in this session

### Provider adapter

A narrow interface that translates provider-specific calls and errors into application contracts.

### Transient failure

A temporary error that may be eligible for a bounded retry.

### Overall deadline

The maximum elapsed time across attempts, waits and processing for a request.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Provider adapter

A provider adapter translates the upstream interface into your application’s draft and failure states. Keep vendor fields and raw exceptions inside that boundary. The baseline receives simulated status/duration/wait tuples, which lets you test orchestration without a key. It establishes neither measured network latency nor the reliability of a real provider.

## Step 2 · Transient failure

A transient failure may be retried only under an explicit policy. Here 429 and 503 are eligible; 403 is permanent and must stop immediately. Retrying every error wastes money and can repeat effects. Generation retries and uncertain remote writes need different policies; an idempotency ledger is introduced later for the latter.

## Step 3 · Overall deadline

An overall deadline counts every attempt and backoff wait. Check remaining time before another wait or call, and state whether a response at the boundary is accepted. This lesson rejects elapsed time greater than or equal to the deadline. Exponential backoff must be bounded by the remaining allowance and maximum attempts.

```python
def generate(outcomes, deadline=5, max_attempts=3):
    if deadline <= 0 or type(max_attempts) is not int or max_attempts < 1:
        raise ValueError('positive deadline and attempts required')
    elapsed = 0
    for attempt, (status, duration, wait) in enumerate(outcomes[:max_attempts], 1):
        elapsed += duration
        if elapsed >= deadline:
            return ('deadline', attempt, elapsed)
        if status == 200:
            return ('draft', attempt, elapsed)
        if status not in (429, 503):
            return ('permanent_failure', attempt, elapsed)
        if attempt == max_attempts or elapsed + wait >= deadline:
            return ('retry_stopped', attempt, elapsed)
        elapsed += wait
    return ('no_more_fixture_responses', attempt if outcomes else 0, elapsed)
assert generate([(429, 1, 2), (200, 1, 0)]) == ('draft', 2, 4)
assert generate([(403, 1, 0), (200, 1, 0)]) == ('permanent_failure', 1, 1)
assert generate([(503, 2, 4), (200, 1, 0)])[0] == 'retry_stopped'
print('transient retry: 2 calls, 4 simulated seconds; permission failure: 1 call')
```

## Walk through the mechanism and its limits

Each tuple is a fake response: status, request duration, requested backoff. The total deadline covers requests and waits, while max_attempts bounds calls. A permanent authorization failure terminates immediately. This does not enforce a socket timeout: a real adapter must pass the remaining deadline to its network client. The example retries read-only generation, not external writes.

## From retry arithmetic to an actual asynchronous deadline

## Before this studio

Sessions 2 and 4: run a Python file, inspect exceptions and distinguish a draft from success. This studio introduces async syntax explicitly; no asynchronous SDK is required.

## Step 1 · Read a coroutine as a paused operation

An async def function returns a coroutine. Calling it alone does not run its body. await runs that operation and lets the event loop schedule other waiting work. asyncio.run creates the loop for this one-file script. Here transport is a function supplied by the caller: a real HTTP adapter and this fixture can expose the same awaitable interface. A synchronous blocking HTTP client inside transport would prevent timely cancellation; choose an asynchronous client for real I/O.

## Step 2 · Classify before deciding to retry

Transient and Permanent are separate exception types. Only Transient is caught inside the retry loop. A permanent credential failure therefore escapes immediately; it cannot turn into an invented draft or another paid attempt. The function returns only the actual transport result. Attempts bound calls, while the exponential delay bounds repeated pressure. Never apply this read-only policy to a write whose remote result is uncertain.

## Step 3 · Put the deadline around the entire operation

asyncio.timeout surrounds both await transport() and await sleep(). Its budget includes waiting and backoff, rather than restarting for every attempt. When the budget expires, cancellation reaches the blocked coroutine; its finally block runs before TimeoutError reaches the caller. Events record that execution entered and cleanup happened. The test does not assert an exact 20ms observation, because scheduler delays vary; it asserts the required cleanup state.

## Step 4 · Keep tests and performance claims separate

Predict two calls for the transient-then-success case, an escaping Permanent for bad credentials, and an observed TimeoutError plus cleanup for a transport that never completes. The events avoid depending on a guessed sleep to prove that work started. These tests exercise actual event-loop cancellation, but no provider, network latency or model quality. The capstone timeout mode is still explicit failure injection, not a measured provider timeout.

## Complete worked example

Save this entire block as example.py in a fresh directory. Run `python3.12 -I example.py` with assertions enabled. All imports are included; no account, provider call or other course is required.

```python
"""Read-only retries: executable fixture transport, no provider calls."""
import asyncio

class Transient(Exception):
    pass

class Permanent(Exception):
    pass

async def generate(transport, *, budget=.2, attempts=3):
    if budget <= 0 or type(attempts) is not int or not 1 <= attempts <= 5:
        raise ValueError('bounded deadline and attempts required')
    # The outer deadline includes execution, waiting and backoff.
    async with asyncio.timeout(budget):
        for number in range(attempts):
            try:
                return await transport()
            except Transient:
                if number + 1 == attempts:
                    raise
                await asyncio.sleep(min(.001 * 2 ** number, .01))
    raise AssertionError('unreachable')

async def demonstrate():
    calls = 0
    async def transient_then_ok():
        nonlocal calls
        calls += 1
        if calls == 1:
            raise Transient('fixture unavailable')
        return {'status': 'draft', 'usage': None}
    assert (await generate(transient_then_ok))['status'] == 'draft'
    assert calls == 2
    async def unauthenticated():
        raise Permanent('fixture credentials rejected')
    try:
        await generate(unauthenticated)
    except Permanent:
        pass
    else:
        raise AssertionError('permanent failure was hidden')
    entered = asyncio.Event()
    cleaned = asyncio.Event()
    async def blocked():
        entered.set()
        try:
            await asyncio.Event().wait()
        finally:
            cleaned.set()
    try:
        await generate(blocked, budget=.02)
    except TimeoutError:
        pass
    else:
        raise AssertionError('deadline ignored')
    assert entered.is_set() and cleaned.is_set()
    print('transient: 2 calls; permanent: propagated; deadline: cleanup completed')

if __name__ == '__main__':
    asyncio.run(demonstrate())
```

## Diagnose and explain

An unawaited-coroutine warning means the function was called without await or asyncio.run. More than two calls means the bound is wrong. A TimeoutError in the exhaustion test means your deliberately tiny deadline, rather than attempt exhaustion, ended it; keep the generous .2-second fixture budget. Real client connection/read/write limits must also respect the overall budget.
