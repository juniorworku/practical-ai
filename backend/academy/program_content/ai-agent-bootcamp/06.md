## Understand the decision: Context budgets and source selection

## Why this decision matters

A context window is finite, and including more text can dilute relevant evidence. Treat selection as an engineering decision: reserve space for instructions, the question, source metadata, and output before choosing passages. Count tokens using the actual provider’s supported tooling when integrating it; a character estimate is only a heuristic.

Preserve source identity when shortening context. Never truncate a policy halfway through a condition and then present the fragment as complete evidence. If relevant content does not fit, choose a smaller scoped question, summarize with traceable references, or return a limitation. Measure how selection changes your evaluation results.

## Vocabulary used in this session

### Context budget

A bounded allocation for instructions, question, source metadata, passages and output.

### Traceable truncation

Omissions are recorded while source identity and meaningful conditions are retained.

### Token estimate

An approximation that must not be reported as measured provider usage.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Context budget

A context budget reserves space before selecting passages: window minus instructions, tools, history and expected output. Metadata also consumes capacity. In the fixture the remaining passage allowance is 260 supplied units. Spending the output reserve on another passage risks truncating the generated response; reject impossible fixed allocations before generation.

## Step 2 · Traceable truncation

Traceable truncation preserves whole rule-and-exception sections and records omitted IDs. Ranked greedy selection can skip a large section and admit a smaller later one; it optimizes neither relevance nor passage count automatically. Inspect whether the omitted section contains the decisive condition, then compare support on the same questions.

## Step 3 · Token estimate

A token estimate is useful for preflight but is not billed usage. The supplied counts are fixture values. A real tokenizer or provider count has its own version and input format; completed usage can differ. Compare one, three and five passages under the same quality threshold, retaining latency and all-attempt cost alongside support review.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
def pack(window, fixed, reserve, passages):
    budget = window - sum(fixed.values()) - reserve
    if budget < 0:
        raise ValueError('instructions and output exceed context window')
    selected, omitted = [], []
    for passage in passages:
        if passage['tokens_including_metadata'] <= budget:
            selected.append(passage['id'])
            budget -= passage['tokens_including_metadata']
        else:
            omitted.append(passage['id'])
    return selected, omitted, budget
passages = [{'id':'returns-rule-and-exception','tokens_including_metadata':180},
            {'id':'shipping','tokens_including_metadata':150},
            {'id':'contact','tokens_including_metadata':90}]
result = pack(1000, {'system':180,'tools':120,'history':240}, 200, passages)
assert result == (['returns-rule-and-exception'], ['shipping','contact'], 80)
print(result)
```

## Walk through the mechanism and its limits

The available retrieval budget is 1000 − 180 − 120 − 240 − 200 = 260. Selecting the 180-token policy leaves 80, insufficient for either later passage. Whole passages preserve exceptions and metadata. These are supplied token counts, not a tokenizer: actual model-specific counts must be measured before a live request. Ordering is a relevance assumption, not an optimal packing algorithm.
