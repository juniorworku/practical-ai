## Why this decision matters

A tool exposes a narrow operation with validated arguments, documented effects, and a known failure contract. The model proposes an argument value; the application establishes the user’s identity and authority. Never accept an account ID supplied by a prompt as proof that the requester owns that account.

Separate tools that read from tools that change external state. Start with `lookup_policy` and a synthetic `lookup_order`. Return only necessary fields. A tool description should explain allowed inputs, possible errors, and whether the operation changes state. Restrict dispatch to an allowlist; do not evaluate arbitrary function names or command text.

## Vocabulary used in this session

### Tool contract

Validated inputs, outputs, side effects, permissions and failure behavior for an operation.

### Owner scope

Access derived from the authenticated user’s authority rather than a model-supplied identity.

### Allowlisted dispatch

Only explicitly registered operation names can be invoked.

## Worked implementation: Tools as typed, permissioned interfaces

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
POLICIES = {'p1': {'owner':'acme', 'text':'Unopened: 14 days.'}}
def dispatch(actor, name, arguments):
    if name != 'lookup_policy':
        return {'error':'unknown_tool'}
    if type(arguments) is not dict or set(arguments) != {'policy_id'} or type(arguments['policy_id']) is not str:
        return {'error':'invalid_arguments'}
    record = POLICIES.get(arguments['policy_id'])
    if record is None or record['owner'] != actor:
        return {'error':'not_found'}
    return {'id':arguments['policy_id'], 'text':record['text']}
assert dispatch('acme','lookup_policy',{'policy_id':'p1'})['id'] == 'p1'
assert dispatch('other','lookup_policy',{'policy_id':'p1'}) == {'error':'not_found'}
assert dispatch('acme','lookup_policy',{'policy_id':'p1','owner':'other'}) == {'error':'invalid_arguments'}
assert dispatch('acme','send_files',{}) == {'error':'unknown_tool'}
print('authorized lookup passed; cross-owner, injected identity and unknown tool blocked')
```

## Walk through the mechanism and its limits

actor is supplied by the application’s authenticated context, never copied from model arguments. Exact argument keys reject an injected identity. The tool returns only allowed fields, and an inaccessible record uses the same public error as an absent one. The example omits HTTP authentication on purpose; later API work must establish actor before calling this dispatcher.

## Worked example

A support tool accepts `order_reference` but derives the tenant from the authenticated user. A request for another tenant’s order returns a permission-safe not-found response. The tool may return shipment status and a timestamp, but it should not expose payment details merely because they exist in the database.

- Unknown tools cannot be dispatched.
- Read results exclude unnecessary sensitive fields.
