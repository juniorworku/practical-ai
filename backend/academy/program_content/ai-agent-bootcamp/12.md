## Why this decision matters

Approval is a server-enforced state transition tied to a concrete action, not a sentence saying “please confirm.” Bind a proposed action to its exact arguments, owner, evidence, revision, and expiry. If any of those change, require review again. Keep an audit record of who approved and what actually executed.

An idempotency key prevents a repeated request from creating duplicate effects within a defined scope. It does not authorize the action and does not guarantee correctness of a remote system. Store action state before attempting execution, and handle an uncertain outcome when a network timeout leaves the remote result unknown.

## Vocabulary used in this session

### Bound approval

Human authorization tied to exact arguments, owner, revision and expiry.

### Idempotency key

A scoped identifier used to recognize a repeated operation without duplicating its effect.

### Uncertain outcome

A remote action may have occurred, but local evidence cannot yet confirm the result.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Bound approval

Bound approval authorizes the exact owner, recipient, content, revision and expiry. Hash a canonical payload to detect changes, then recheck actor authority immediately before the effect. A digest is not encryption and does not itself identify a reviewer. Changing the recipient must require new approval even if the text stays the same.

## Step 2 · Idempotency key

An idempotency key identifies the same intended operation across retries. Store a scoped key with a database uniqueness constraint before dispatch. Two connections must not both claim it. Reusing a key with different payload is a conflict, not permission to silently execute new work. Local uniqueness only governs your ledger.

## Step 3 · Uncertain outcome

An uncertain outcome means the remote service may have accepted the operation before the response was lost. Preserve the same key and reconcile against an authoritative remote observation. A local rollback cannot unsend a remote message. Do not mark uncertain as failed and create a fresh key just to get a green result.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
import hashlib, json
def digest(payload):
    return hashlib.sha256(json.dumps(payload,sort_keys=True,separators=(',',':')).encode()).hexdigest()
payload = {'owner':'acme','recipient':'local-reviewer','content':'Policy draft','revision':2}
approval = {'digest':digest(payload),'actor':'lead','expires':10}
ledger, effects = {}, []
def execute(data, now, actor_active=True, lose_response=False, actor='lead'):
    if actor!=approval['actor'] or not actor_active or now >= approval['expires'] or digest(data) != approval['digest']:
        return 'needs_review'
    key = data['owner']+':a7:r'+str(data['revision'])
    if key in ledger:
        return 'reconcile_existing' if ledger[key]=='uncertain' else 'already_committed'
    ledger[key] = 'claimed'
    effects.append((key,dict(data)))  # Local fake destination; no external send.
    ledger[key] = 'uncertain' if lose_response else 'committed'
    return ledger[key]
assert execute(dict(payload, recipient='changed'),1) == 'needs_review'
assert execute(payload,1,actor_active=False) == 'needs_review'
assert execute(payload,10) == 'needs_review'
assert execute(payload,1,actor='other')=='needs_review'
assert execute(payload,1,lose_response=True) == 'uncertain'
assert execute(payload,2) == 'reconcile_existing' and len(effects)==1
print('one fake effect; lost response remains uncertain until reconciled')
```

## Walk through the mechanism and its limits

The digest binds effect fields to the reviewed payload. Expiry and actor authority are checked again before execution. The fake destination records an effect before losing the response, so a retry must reconcile the same key rather than send again. This single-process dictionary does not provide an atomic multi-worker claim or crash durability. A database constraint/transaction and destination-specific idempotency are required for those claims.
