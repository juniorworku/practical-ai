## Why this decision matters

An API boundary translates between user input and application behavior. Validate payloads at entry, derive identity from authentication, and return predictable status codes and error shapes. Avoid accepting arbitrary URLs for retrieval: doing so introduces an outbound network capability that your offline policy assistant does not need.

Separate a request being accepted from a result being ready. For a synchronous prototype, return a completed answer or a clear failure within a bound. If you later add jobs, expose durable job IDs and state rather than holding a request open forever. Document errors as part of the contract, not just the success example.

## Vocabulary used in this session

### Request validation

Enforcing required fields, sizes, types and allowed values at the API boundary.

### Server identity

The authenticated principal established independently of client-supplied owner fields.

### Accepted versus complete

A received request or queued job is not necessarily a finished result.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Request validation

Request validation belongs at the HTTP boundary: reject missing/extra fields, wrong types and oversized or blank questions before calling a provider. A serializer in your DRF endpoint should enforce the same rules as this application-layer fixture. Keep useful failure categories in the response without exposing raw upstream exceptions or credentials.

## Step 2 · Server identity

Server identity is established by authentication, then passed to application code separately from the submitted body. The baseline TOKENS dictionary is synthetic scaffolding, not a production login system. A client-supplied owner field must not override the principal. Verify rejected authentication never reaches a provider or saves a draft under someone else.

## Step 3 · Accepted versus complete

Accepted work is not completed work. A saved draft needing review can legitimately return a created-record response while remaining unapproved. A provider timeout should retain recoverable user input and expose failure. A queued real endpoint needs an explicit job status/readback contract rather than a success label while processing is still pending.

## Worked implementation: HTTP contracts and a usable API

## Walk through the data and decision

1. An unknown token returns 401 before body processing.

2. Valid identity with bad fields returns 400 without calling the provider.

3. A timeout returns 503 with retained question, generation_failed status and no private exception detail.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
# Application boundary only: no web server or real identity provider.
TOKENS = {'test-acme':'acme'}
def post_draft(token, body, provider):
    actor = TOKENS.get(token)
    if actor is None:
        return 401, {'error':'authentication_required'}
    if type(body) is not dict or set(body) != {'question'} or type(body['question']) is not str:
        return 400, {'error':'invalid_fields'}
    question = body['question'].strip()
    if not question or len(question)>500:
        return 400, {'error':'invalid_question'}
    draft = {'owner':actor,'question':question,'status':'pending'}
    try:
        draft['answer'] = provider(question)
        draft['status'] = 'needs_review'
    except TimeoutError:
        draft['status'] = 'generation_failed'
        return 503, {'error':'provider_unavailable','draft':draft}
    return 201, draft
assert post_draft('bad',{},lambda q:'x')[0] == 401
assert post_draft('test-acme',{'question':''},lambda q:'x')[0] == 400
assert post_draft('test-acme',{'question':'Returns?'},lambda q:'14-day unopened policy')[0] == 201
def unavailable(question):
    raise TimeoutError('synthetic private provider details')
status, result = post_draft('test-acme',{'question':'Returns?'},unavailable)
assert status == 503 and result['draft']['question']=='Returns?'
assert 'synthetic private' not in str(result)
print('401 authentication; 400 input; 201 draft; 503 recoverable provider failure')
```

## Expected observation

```text
401 authentication; 400 input; 201 draft; 503 recoverable provider failure
```

## Walk through the mechanism and its limits

Authentication precedes validation. Exact fields reject client-supplied ownership. Failure returns a stable category and retains the question, without exposing raw exception text. The returned draft is not durable yet: the persistence lesson adds that boundary. 503 here means synchronous generation failed; it is not a promise that a background job will finish.
