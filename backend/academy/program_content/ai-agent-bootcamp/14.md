## Understand the decision: Persistence, transactions, and data ownership

## Before you begin

## Why this decision matters

Persist sources, runs, notes, and action records with explicit owners and lifecycle fields. Database constraints protect invariants even when two requests arrive together. A check-then-insert in Python alone is not sufficient to prevent concurrent duplicate records. Use unique constraints and transaction boundaries appropriate to the operation.

Decide what must commit together. Saving a user’s work should not depend on an optional model request succeeding. Keep prompt drafts and operational metadata separate from secrets. Define deletion and retention rules for source content and run traces. A backup is useful only when you can demonstrate a restore into an isolated database.

## Vocabulary used in this session

### Database invariant

A condition backed by constraints, such as unique owner-and-action keys.

### Transaction

A boundary within which related database changes commit or roll back together.

### Optional side effect

Work such as model feedback that must not erase already saved user data if it fails.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Database invariant

A database invariant protects state even when two callers bypass the same screen. A unique owner/key pair prevents duplicate records, while an expected version prevents stale overwrites. Include owner in the conditional update. Reading the whole table and checking ownership in the browser is too late and leaks data.

## Step 2 · Transaction

A transaction groups related database writes so they commit or roll back together. In the baseline the draft update and audit insertion form one unit; a forced audit failure restores the original draft. The transaction does not cover effects outside the database, such as sending a message or changing a separate service.

## Step 3 · Optional side effect

An optional side effect must not make the primary save falsely disappear. Persist the draft and a pending outbox record together, then dispatch separately with an operation key and reconciliation policy. A failed notification can leave the draft saved and the notification pending. Show these as separate states rather than one ambiguous success flag.

```python
import sqlite3
from tempfile import TemporaryDirectory
from pathlib import Path
with TemporaryDirectory() as folder:
    path = Path(folder)/'drafts.sqlite'
    db = sqlite3.connect(path)
    db.executescript('CREATE TABLE drafts(owner TEXT, key TEXT, version INT, body TEXT, UNIQUE(owner,key)); CREATE TABLE audit(event TEXT);')
    with db:
        db.execute('INSERT INTO drafts VALUES(?,?,?,?)',('acme','d1',4,'original'))
    def save(owner, key, version, text, fail=False):
        try:
            with db:
                changed = db.execute('UPDATE drafts SET body=?,version=version+1 WHERE owner=? AND key=? AND version=?',(text,owner,key,version)).rowcount
                if changed != 1:
                    return 'conflict_or_inaccessible'
                if fail:
                    raise RuntimeError('audit failed')
                db.execute('INSERT INTO audit VALUES(?)',('saved',))
        except RuntimeError:
            return 'rolled_back'
        return 'saved'
    assert save('acme','d1',4,'correction') == 'saved'
    assert save('acme','d1',4,'stale') == 'conflict_or_inaccessible'
    assert save('other','d1',5,'attack') == 'conflict_or_inaccessible'
    assert save('acme','d1',5,'partial',True) == 'rolled_back'
    db.close()
    db = sqlite3.connect(path)
    assert db.execute('SELECT version,body FROM drafts').fetchone() == (5,'correction')
    assert db.execute('SELECT count(*) FROM audit').fetchone()[0] == 1
    db.close()
print('version 5 survives reopen; stale, cross-owner and partial saves rejected')
```

## Walk through the mechanism and its limits

The UPDATE compares owner, key and expected version in the same database statement. A successful write increments the version. The audit insertion and update share a transaction; raising before audit completion rolls both back. Reopening the file proves server-side file persistence rather than a variable retaining data. SQLite teaches the invariant locally; PostgreSQL concurrency behavior must be tested in your actual app.

## Prove approval rollback before wiring the HTTP route

## Before this studio

Session 12 supplies exact-payload approval and a scoped operation key; session 14 introduces transactions. SQL placeholders, uniqueness and connection closure are explained here.

## Step 1 · Model two records with one invariant

drafts stores the reviewable text and state. effects stores the local outbox receipt under a primary key. The invariant is that an approved draft has exactly one matching local effect. A unique key blocks duplicate receipts, but does not by itself keep the draft status consistent. This studio uses one connection to make transaction behavior easy to inspect; the final PostgreSQL implementation additionally locks the selected owner-scoped row.

## Step 2 · Separate committed setup from the operation

The initial draft is committed before approve runs. Otherwise an injected exception could roll back fixture creation and make a test pass for the wrong reason. with db commits its block on success and rolls it back on an escaping exception. It does not close the SQLite connection: closing handles that separately. SQL ? placeholders bind values rather than interpolating reviewed text into executable SQL.

## Step 3 · Inject failure between the two writes

approve inserts the receipt, then fail=True raises before updating the draft. The exception escapes the transaction block, rolling back the inserted receipt. Predict zero effects and needs_review. A later normal call commits both writes. Replaying the same ID uses INSERT OR IGNORE and returns the same receipt. This demonstrates local atomicity and replay, not arbitrary distributed concurrency or external delivery.

## Step 4 · Carry the invariant into PostgreSQL

In the final app, trusted server identity supplies owner and reviewer role. SELECT FOR UPDATE must execute inside transaction.atomic and include the owner predicate. Compare the submitted version and digest to the locked payload before creating the receipt. A database rollback can remove a local outbox row; it cannot unsend a remote message. An uncertain remote result requires reconciliation, not a second unqualified send.

## Complete worked example

Save this entire block as example.py in a fresh directory. Run `python3.12 -I example.py` with assertions enabled. All imports are included; no account, provider call or other course is required.

```python
"""Transaction rollback and durable local approval, not remote exactly-once."""
from contextlib import closing
import sqlite3

def approve(db, owner, draft, reviewed_text, *, fail=False):
    # This single-connection teaching model does not implement concurrent locking.
    with db:
        row = db.execute('SELECT owner,text,state FROM drafts WHERE id=?', (draft,)).fetchone()
        if row is None or row[0] != owner:
            raise PermissionError('draft owner')
        if reviewed_text != row[1]:
            raise ValueError('stale review')
        if row[2] not in {'needs_review', 'approved'}:
            raise ValueError('draft not approvable')
        receipt = 'effect:' + draft
        db.execute('INSERT OR IGNORE INTO effects VALUES (?,?)', (receipt, row[1]))
        if fail:
            raise RuntimeError('failure before status update')
        db.execute('UPDATE drafts SET state=? WHERE id=?', ('approved', draft))
    return receipt

with closing(sqlite3.connect(':memory:')) as db:
    db.executescript('CREATE TABLE drafts(id TEXT PRIMARY KEY,owner TEXT,text TEXT,state TEXT);'
                     'CREATE TABLE effects(id TEXT PRIMARY KEY,text TEXT);')
    db.execute('INSERT INTO drafts VALUES (?,?,?,?)', ('d1', 'one', '14 days, unopened only', 'needs_review'))
    db.commit()  # Persist the setup separately from the transaction being tested.
    try:
        approve(db, 'one', 'd1', '14 days, unopened only', fail=True)
    except RuntimeError:
        pass
    assert db.execute('SELECT count(*) FROM effects').fetchone()[0] == 0
    assert db.execute('SELECT state FROM drafts').fetchone()[0] == 'needs_review'
    first = approve(db, 'one', 'd1', '14 days, unopened only')
    assert approve(db, 'one', 'd1', '14 days, unopened only') == first
    assert db.execute('SELECT count(*) FROM effects').fetchone()[0] == 1
print('rollback: no effect; retry and replay: one local receipt')
```
