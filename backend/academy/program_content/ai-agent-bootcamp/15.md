## Understand the decision: Design reviewable user experiences

## Before you begin

## Why this decision matters

A useful AI interface helps a user judge and correct a result. Show the question, draft status, source excerpts, revision, and an obvious next step. Distinguish generated suggestions from executed actions. A spinning indicator without cancellation or timeout behavior creates confusion when the backend fails.

Keep the user’s input when errors occur. Provide keyboard-accessible controls and meaningful status messages. Test with a person who did not build the interface: ask them to locate a citation and explain whether an action happened. If they cannot, the interface is making claims the system cannot support.

## Vocabulary used in this session

### Reviewable draft

An output whose evidence, status and suggested changes are inspectable by the user.

### Failure recovery UX

A visible error with retained input and an explicit next action.

### Action status

A label reflecting actual execution state rather than a generated suggestion.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Reviewable draft

A reviewable draft makes its status and source visible before the user acts. “Generated” means text exists, not that it has been approved. Keep review-required and approved states separate, and bind approval to a revision. The fixture disables export for all states deliberately; the practice adds the missing approval-aware transition.

## Step 2 · Failure recovery UX

Failure recovery preserves the user’s question, explains what failed and offers a meaningful next action. A loading spinner must stop on an error. Use associated input labels and an announced status in the real interface. Test a disconnected API through the browser; a Python state dictionary alone cannot establish keyboard usability or retained form input.

## Step 3 · Action status

Action status describes what actually happened: queued, running, failed, uncertain or confirmed. Avoid turning a returned HTTP response into an approved export. If the user edits an approved draft, its old approval must become stale. Expose that change immediately so a polished button cannot hide an unreviewed revision.

## Worked implementation: Design reviewable user experiences

## Walk through the data and decision

1. loading sets busy true without enabling export.

2. failed retains the question and enables retry while clearing busy.

3. review remains unapproved even though a draft is available.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
def view(state, question, error=None):
    labels = {'idle':'Ask a policy question','loading':'Generating draft',
              'review':'Draft needs review','clarify':'More information needed',
              'abstain':'No supporting policy','failed':'Generation failed'}
    if state not in labels:
        raise ValueError('unknown UI state')
    return {'label':labels[state], 'question':question,
            'retry':state=='failed', 'export_enabled':False,
            'busy':state=='loading', 'error':error if state=='failed' else None}
question = 'Can I return this item?'
assert view('loading',question)['busy']
failed = view('failed',question,'Please retry; your question is retained.')
assert failed['question']==question and failed['retry'] and not failed['busy']
assert not view('review',question)['export_enabled']
print('loading, review and failure remain distinct; input retained; export unapproved')
```


## Walk through the mechanism and its limits

This is a view-state contract, not a rendered React interface. It separates machine completion from human approval, always retains the input, and exposes an explicit retry affordance after failure. Disabling export here models a draft-only release; a future reviewed export needs a separate approved revision. State assertions cannot establish keyboard usability or whether labels make sense to people.
