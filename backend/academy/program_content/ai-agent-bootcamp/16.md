# Build a regression harness

## Understand the decision: Build a regression harness

## Before you begin

## Why this decision matters

An evaluation harness executes the same cases through the same system version and records comparable results. Separate deterministic contract tests from quality judgments. Exact matching is appropriate for status labels and source identifiers; supported answer meaning may require a rubric and human review.

Report denominators. “90% accuracy” over ten easy questions conceals both sample size and failure distribution. Break results down by answerable, missing-evidence, ambiguous, and adversarial cases. Preserve the raw observed result and annotate the failure category so that fixes target the responsible stage: ingestion, retrieval, generation, validation, or UI.

## Vocabulary used in this session

### Regression harness

A repeatable run of named cases against a recorded system and dataset revision.

### Failure denominator

The total relevant cases, including failed or unavailable runs, used to interpret a result.

### Category analysis

Separate outcomes for groups such as ambiguous, missing-evidence and adversarial cases.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Regression harness

A regression harness sends actual inputs through an executable candidate and compares its outputs with independently prepared labels. Keep expected labels outside the request. Literal expected/observed tuples can illustrate counting but cannot show a system was tested. Fix the dataset and candidate revisions so improvements can be reproduced.

## Step 2 · Failure denominator

The failure denominator includes every attempted case, including unavailable results and exceptions. A system that answers two easy questions and drops two failures has not achieved perfect accuracy. Record unavailable separately from an incorrect completed answer while retaining both in the attempted population. Missing usage also stays unknown rather than zero.

## Step 3 · Category analysis

Category analysis catches regressions hidden by averages. Separate ordinary, ambiguous, missing-evidence and unauthorized requests, then declare critical gates before running. One unauthorized disclosure can block promotion despite a higher aggregate pass rate. Compare identical cases and inspect the strongest counterexample rather than only reporting a single percentage.

## Walk through the data and decision

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
# Expected labels stay outside candidate requests.
def candidate(request):
    if request['scope']!='acme':return 'answer'  # Deliberate defect to detect.
    if not request['has_source']:return 'abstain'
    return 'answer'  # Deliberate missing-condition defect.
cases=[{'category':'normal','input':{'scope':'acme','has_source':True,'condition':'unopened'},'expected':'answer'},
       {'category':'ambiguous','input':{'scope':'acme','has_source':True,'condition':None},'expected':'clarify'},
       {'category':'missing','input':{'scope':'acme','has_source':False,'condition':'unopened'},'expected':'abstain'},
       {'category':'security','input':{'scope':'other','has_source':True,'condition':'unopened'},'expected':'deny'}]
counts={};critical=[]
for case in cases:
    actual=candidate(dict(case['input']))
    row=counts.setdefault(case['category'],[0,0]);row[0]+=int(actual==case['expected']);row[1]+=1
    if case['category']=='security' and actual!=case['expected']:critical.append(case['category'])
passed=sum(a for a,b in counts.values())
assert passed==2 and len(cases)==4 and critical==['security']
print({'passed':passed,'total':len(cases),'categories':counts,'promote':False})
```

## Walk through the mechanism and its limits

Each row has category, expected behavior and observed behavior. Every case contributes to its denominator, including incorrect answers and unavailable outcomes. The security failure independently blocks promotion even if an aggregate threshold passes. The expected labels are fixture judgments; scoring real factual support requires a rubric and a reviewer, not exact string comparison alone.

A notebook or chat demo is an early prototype. Completion requires operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to A release candidate tested against normal and edge-case inputs

### Latency vs. Cost vs. Quality

Report latency distributions, total spend, acceptance and critical failures by category. A cheap/fast candidate cannot trade away a mandatory safety or factual-support gate.

### Deterministic Evaluation

Freeze dataset, prompt, model, parser and judge versions. Fail CI on schema/permission regressions; run model-based quality judgments with recorded rubrics and reviewed disagreements.

### Context Management

Compare context sizes and cache policies using the same dataset. Log counts, hit/miss and revision IDs without copying private prompts into traces.

## Failure and deployment work

Trace retries, timeouts and queue wait as separate spans. Redact logs, retain unavailable runs in denominators and rehearse promotion/rollback.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
