# Build a regression harness

## Understand the decision: Build a regression harness

## Before you begin

Complete sessions 1–15 in this bootcamp. Keep your policy fixtures and evaluation labels in your own workspace. The example below runs independently so a prior missing file cannot block understanding.

## Why this decision matters

An evaluation harness executes the same cases through the same system version and records comparable results. Separate deterministic contract tests from quality judgments. Exact matching is appropriate for status labels and source identifiers; supported answer meaning may require a rubric and human review.

Report denominators. “90% accuracy” over ten easy questions conceals both sample size and failure distribution. Break results down by answerable, missing-evidence, ambiguous, and adversarial cases. Preserve the raw observed result and annotate the failure category so that fixes target the responsible stage: ingestion, retrieval, generation, validation, or UI.

## Vocabulary used in this session

### Regression harness

A repeatable run of named cases against a recorded system and dataset revision.

### Failure denominator

The total relevant cases, including failed or unavailable runs, used to interpret a result.

### Category analysis

Separate outcomes for groups such as ambiguous, missing-evidence and adversarial cases.

## Worked implementation: Build a regression harness

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
from collections import defaultdict
cases = [('normal','answer','answer'),('ambiguous','clarify','answer'),
         ('missing','abstain','abstain'),('security','deny','answer')]
counts = defaultdict(lambda:[0,0])
for category, expected, observed in cases:
    counts[category][0] += int(expected==observed)
    counts[category][1] += 1
passed = sum(a for a,b in counts.values())
critical = [c for c,e,o in cases if c=='security' and e!=o]
assert passed==2 and len(cases)==4 and critical==['security']
assert not (passed/len(cases) >= .5 and not critical)
print({'passed':passed,'total':len(cases),'categories':dict(counts),'promote':False})
```

## Expected observation

```text
{'passed': 2, 'total': 4, 'categories': {'normal': [1, 1], 'ambiguous': [0, 1], 'missing': [1, 1], 'security': [0, 1]}, 'promote': False}
```

## Walk through the mechanism and its limits

Each row has category, expected behavior and observed behavior. Every case contributes to its denominator, including incorrect answers and unavailable outcomes. The security failure independently blocks promotion even if an aggregate threshold passes. The expected labels are fixture judgments; scoring real factual support requires a rubric and a reviewer, not exact string comparison alone.

## Build and challenge your own version

## Worked example

For 20 cases, your retriever finds the supporting passage in 16, but only 12 answers are fully supported. Improving retrieval alone cannot explain the remaining generation errors. A system that abstains on all cases has excellent non-fabrication but zero useful-answer coverage.

## Build it yourself

1. Write a harness that saves case ID, system revision, selected sources, outcome, and rubric judgments.
2. Run the fake baseline and one improved version against the development split.
3. Review failures by category and choose one change supported by the evidence.
4. Run the holdout split once for the release candidate and preserve that report.

## Break it deliberately

A change raises overall pass rate while making all conflict cases worse. Your report should make that regression visible instead of hiding it in the average.

## Acceptance checks

- Reports include counts and category-level outcomes.
- The system revision and evaluation dataset revision are recorded.
- A quality trade-off is supported by observed cases.
