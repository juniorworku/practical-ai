## Understand the decision: Prompt injection and untrusted documents

## Why this decision matters

A retrieved document can contain instructions that conflict with the user’s task. Treat its text as data even when it claims to be a system message or an administrator. Prompt wording is only one defense; tool permissions, data access, action approval, and output validation must remain enforced by application code.

Threat-model the assets and trust boundaries: private documents, provider credentials, source retrieval, model output, tool dispatch, and external actions. A successful attack is defined by an unauthorized disclosure or effect, not merely the model repeating suspicious words. Use synthetic canary values and local fake tools when testing.

## Vocabulary used in this session

### Prompt injection

Untrusted content attempts to redirect the system’s behavior or authority.

### Trust boundary

A separation where data from one source cannot automatically grant privileges in another.

### Canary fixture

A synthetic recognizable value used to test unauthorized disclosure without real secrets.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Prompt injection

Prompt injection puts instructions inside untrusted content: a retrieved note might ask the assistant to ignore policy and send files. Treat such text as evidence to interpret, never as authority to change permissions. The baseline uses adversarial proposals directly, so it tests the enforcement boundary without claiming to measure a real model’s susceptibility.

## Step 2 · Trust boundary

A trust boundary separates document text and model proposals from server-established actor permissions. Reject forbidden operations and check scope even for an allowed read tool. An allowlist alone does not prevent an allowed tool from reading another owner’s record. Also inspect the returned projection, traces and error messages for accidental disclosure.

## Step 3 · Canary fixture

A canary is a synthetic distinctive marker placed where it must not escape. Test its absence in the actual output and exported trace payload, not just a screen that hides it. Passing a few canary cases is regression evidence, not a proof that all secrets are safe. Name a residual risk and keep expanding realistic adversarial cases.

## Walk through the data and decision

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
records = {'p1':{'owner':'acme','text':'Return unopened within 14 days.'},
           'private':{'owner':'other','text':'CANARY-OTHER-SECRET'}}
def lookup(actor, identifier):
    record = records.get(identifier)
    return record['text'] if record and record['owner']==actor else 'inaccessible'
def dispatch(actor, proposed):
    name, identifier = proposed
    if name != 'lookup':
        return 'tool_denied'
    return lookup(actor,identifier)
# These are adversarial model proposals, not commands executed by this file.
results = [dispatch('acme',p) for p in [('send_files','all'),('lookup','private'),('lookup','p1')]]
assert results == ['tool_denied','inaccessible','Return unopened within 14 days.']
assert 'CANARY-OTHER-SECRET' not in str(results)
print('forbidden operation and allowed-tool cross-owner attack both denied')
```

## Walk through the mechanism and its limits

Testing only forbidden tool names misses attacks that abuse an allowed lookup with an unauthorized ID. The ownership check remains inside the tool regardless of what the retrieved document says. Synthetic proposals test enforcement, not whether a particular model resists instructions; those are distinct evaluations. This narrow example cannot establish that every output channel or logging path is safe.

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Graduation builds toward operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. Early checkpoints assess only boundaries already taught; future deployment controls are planned rather than claimed complete. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to A release candidate tested against normal and edge-case inputs

### Latency vs. Cost vs. Quality

Report latency distributions, total spend, acceptance and critical failures by category. A cheap/fast candidate cannot trade away a mandatory safety or factual-support gate.

### Deterministic Evaluation

Freeze dataset, prompt, model, parser and judge versions. Fail CI on schema/permission regressions; run model-based quality judgments with recorded rubrics and reviewed disagreements.

### Context Management

Compare context sizes and cache policies using the same dataset. Log counts, hit/miss and revision IDs without copying private prompts into traces.

## Failure and deployment work

Trace retries, timeouts and queue wait as separate spans. Redact logs, retain unavailable runs in denominators and rehearse promotion/rollback.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
