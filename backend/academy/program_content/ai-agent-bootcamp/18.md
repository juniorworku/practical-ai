## Why this decision matters

Instrumentation should help explain failures without becoming a copy of private user data. Assign a run ID and record stage duration, outcome category, source revision, tool name, and retry count. Do not log API keys or full policy content by default. A metric is useful only when its definition and unit are clear.

Separate measured provider usage from estimates. A fake adapter can validate accounting logic but cannot establish real model prices, throughput, or quality. Measure latency distributions, not just one fast demo. Decide which condition should cause a slower path, human review, or a graceful refusal when a budget is exhausted.

## Vocabulary used in this session

### Run trace

Structured observations such as stage duration, source revision, tool outcome and retry count.

### Usage accounting

Separately recording measured provider usage and estimates.

### Tail latency

The slower end of request durations, which an average can conceal.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Run trace

A run trace records stage, timing, outcome and release identity so a failure can be located. Separate retrieval, generation and review instead of storing one unexplained duration. Minimize payload before exporting logs. A trace containing raw prompts may be easy to debug but can expose private policy or credentials to a new destination.

## Step 2 · Usage accounting

Usage accounting keeps the cost of failed and retried attempts. Divide total workload spend by outputs that meet the agreed reviewed bar to obtain useful-output cost. Zero accepted outputs makes that ratio undefined. Fixture cost units and acceptance labels are supplied assumptions here, not a live provider bill or automatic semantic judgment.

## Step 3 · Tail latency

Tail latency describes the slower population under a named percentile rule. Sort all included timings and use nearest-rank p95 in this lesson. Four observations give a very rough tail estimate; report sample size, timeout handling and warm/cache conditions. A fast candidate that fails the quality floor is not an acceptable optimization.

## Worked implementation: Observability, cost, and latency budgets

## Walk through the data and decision

1. Four attempts cost 14 fixture units but only two are accepted, giving 7 per accepted draft.

2. Nearest-rank p95 selects the fourth sorted timing, 900ms.

3. An additional retry consumes cost without automatically adding another accepted output.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
from math import ceil
runs = [{'ms':100,'cost':2,'accepted':True}, {'ms':120,'cost':3,'accepted':True},
        {'ms':160,'cost':4,'accepted':False}, {'ms':900,'cost':5,'accepted':False}]
latencies = sorted(r['ms'] for r in runs)
accepted = sum(r['accepted'] for r in runs)
unit_cost = sum(r['cost'] for r in runs)/accepted if accepted else None
p95 = latencies[ceil(.95*len(latencies))-1]
assert unit_cost==7 and p95==900
print({'accepted':accepted,'attempts':len(runs),'cost_per_accepted':unit_cost,'p95_ms':p95,'usage_kind':'simulated'})
```

## Expected observation

```text
{'accepted': 2, 'attempts': 4, 'cost_per_accepted': 7.0, 'p95_ms': 900, 'usage_kind': 'simulated'}
```

## Walk through the mechanism and its limits

All four attempts consume the illustrative 14 cost units, but only two accepted drafts supply the useful-output denominator. Nearest-rank p95 selects ceil(.95 × 4) = 4, so the slowest fixture is reported. With four rows this tail estimate is very unstable; no provider speed or price is measured. If acceptance is zero, cost per accepted output is undefined, not zero.

## Production evidence

A notebook or chat demo is an early prototype. Completion requires operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to A release candidate tested against normal and edge-case inputs

### Latency vs. Cost vs. Quality

Report latency distributions, total spend, acceptance and critical failures by category. A cheap/fast candidate cannot trade away a mandatory safety or factual-support gate.

### Deterministic Evaluation

Freeze dataset, prompt, model, parser and judge versions. Fail CI on schema/permission regressions; run model-based quality judgments with recorded rubrics and reviewed disagreements.

### Context Management

Compare context sizes and cache policies using the same dataset. Log counts, hit/miss and revision IDs without copying private prompts into traces.

## Failure and deployment work

Trace retries, timeouts and queue wait as separate spans. Redact logs, retain unavailable runs in denominators and rehearse promotion/rollback.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
