## Why this decision matters

A working local Python process is only one part of the release. A complete deployment needs a frontend, API, database, configuration, networking, static assets, startup ordering, and health checks. Container images package code and dependencies; named volumes preserve database data beyond a container’s lifetime.

Keep credentials in runtime configuration. A database port does not need to be public when only the API uses it. Understand the difference between container-local hostnames and browser-visible URLs: the browser cannot resolve a Compose service name. Use a frontend proxy so requests remain on the same origin. Test the built frontend rather than only a development server.

## Vocabulary used in this session

### Container network

A private network where service names resolve for containers, not necessarily for a browser.

### Persistent volume

Storage that survives removal or replacement of a container.

### Readiness probe

A check of the dependency needed for the service to fulfill its readiness claim.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Container network

A container network provides service names to containers, not to the browser. The page requests relative /api URLs; Nginx resolves backend internally, and the backend resolves db. Publishing PostgreSQL is unnecessary for this path. Trace browser → proxy → API → database before debugging individual endpoints so localhost is not mistaken for the same host everywhere.

## Step 2 · Persistent volume

A persistent volume stores database files outside a replaceable container. Recreating the backend should preserve the saved draft because its data lives in PostgreSQL. A named volume is not a tested backup; deleting it removes the synthetic records. The supplied lab binds only loopback and uses synthetic runtime configuration; it is not an authenticated production deployment.

## Step 3 · Readiness probe

A readiness probe checks a required dependency through an actual query. A running process can still return 503 when PostgreSQL is stopped. Wait for readiness before writing, record the returned draft ID and read it after replacement. Building an image or creating source files alone does not demonstrate end-to-end persistence.

### backend/app.py

```python
import os
from django.conf import settings
settings.configure(
    SECRET_KEY=os.environ["DJANGO_SECRET_KEY"], DEBUG=False,
    ALLOWED_HOSTS=["localhost","127.0.0.1","backend"], ROOT_URLCONF=__name__,
    DATABASES={"default":{"ENGINE":"django.db.backends.postgresql", "NAME":os.environ["POSTGRES_DB"],
      "USER":os.environ["POSTGRES_USER"], "PASSWORD":os.environ["POSTGRES_PASSWORD"], "HOST":"db", "PORT":"5432"}},
    INSTALLED_APPS=["rest_framework"],
    REST_FRAMEWORK={"UNAUTHENTICATED_USER":None},
)
import django
django.setup()
from django.db import connection
from django.urls import path
from django.core.wsgi import get_wsgi_application
from rest_framework.decorators import api_view
from rest_framework.response import Response

@api_view(["GET"])
def health(request):
    try:
        with connection.cursor() as cursor:
            cursor.execute("SELECT 1")
            cursor.fetchone()
        return Response({"database":"postgresql","ready":True})
    except Exception:
        return Response({"ready":False,"error":"database_unavailable"},status=503)

@api_view(["GET","POST"])
def drafts(request):
    # Dedicated synthetic local lab only; no authentication or production migration system.
    with connection.cursor() as cursor:
        cursor.execute("CREATE TABLE IF NOT EXISTS lab_drafts(id SERIAL PRIMARY KEY, body TEXT NOT NULL)")
        if request.method=="POST":
            body=request.data.get("body")
            if type(body) is not str or not body.strip() or len(body)>500:
                return Response({"error":"body_required_max_500"},status=400)
            cursor.execute("INSERT INTO lab_drafts(body) VALUES(%s) RETURNING id",[body.strip()])
            return Response({"id":cursor.fetchone()[0],"body":body.strip()},status=201)
        cursor.execute("SELECT id,body FROM lab_drafts ORDER BY id")
        return Response([{"id":row[0],"body":row[1]} for row in cursor.fetchall()])

urlpatterns=[path("api/health/",health),path("api/drafts/",drafts)]
application=get_wsgi_application()
```

### compose.yaml

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: lab
      POSTGRES_USER: lab
      POSTGRES_PASSWORD: ${LAB_DB_PASSWORD:?Set LAB_DB_PASSWORD}
    volumes:
      - lab-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U lab -d lab"]
      interval: 2s
      timeout: 3s
      retries: 30
  backend:
    build: ./backend
    environment:
      POSTGRES_DB: lab
      POSTGRES_USER: lab
      POSTGRES_PASSWORD: ${LAB_DB_PASSWORD:?Set LAB_DB_PASSWORD}
      DJANGO_SECRET_KEY: ${LAB_DJANGO_SECRET:?Set LAB_DJANGO_SECRET}
    depends_on:
      db:
        condition: service_healthy
  frontend:
    build: ./frontend
    ports:
      - "127.0.0.1:${LAB_PORT:-8091}:80"
    depends_on:
      - backend
volumes:
  lab-data:
```

## Connect the pieces before changing them

1. Read core.py first. Its process(input, mode, documents) function returns a status, text and evidence IDs. It must never receive the expected test answer. The provider is a named scripted fixture, so a passing run proves control flow, not model quality.
2. Read app.py's exact and identity functions. Reject extra fields and blank input before retrieval. Demo bearer strings resolve to a trusted owner/role at the server; a JSON owner field is rejected. These published fixture tokens are local teaching identities, not production authentication.
3. Trace ask: validate → owner-filter persisted sources → core workflow → save result → return ID. A timeout is a stored failed result, not an empty successful answer. Health runs a real query against the required table.
4. initialize is a one-shot schema release job. It creates the records and quota tables before Gunicorn starts. PostgreSQL bucket is a fixed-minute quota window: avoid the reserved SQL word window. Parameterized values stay outside SQL syntax. The ON CONFLICT increment is atomic across both HTTP workers; a Python dictionary counter would not be shared.
5. PostgreSQL JSONB stores an object, but Django raw cursors may return its JSON text. Decode a string at the storage boundary before accessing fields. Do not serialize an already serialized value twice. All reads include owner before payload leaves the database.
6. Approval digests bind text, source version and citations using one canonical server serialization. The UI uses the server's digest rather than trying to recreate Python JSON spacing in JavaScript. The submitted version and digest must match the row locked by SELECT FOR UPDATE. Only reviewer-one can approve owner one's draft. The effect is a local outbox row, never an external message, refund or calendar event.
7. The same transaction writes the local effect and approval status. A stable effect key plus the row lock makes simultaneous duplicate confirmation return the same receipt. A timed-out external write would need reconciliation; this local transaction does not claim distributed exactly-once delivery.
8. Browser code displays response text with textContent and retains the input on errors. It shows the stored result before review. An HTTP 201 says a result was saved; inspect status to distinguish needs_review, failed, abstain, denied or needs_correction.
9. Compose starts an isolated PostgreSQL volume, runs the schema job once, and publishes only the API on loopback. Recreating an API container must retain records because the database volume is separate. Dependency outage yields 503; health is not a substitute for the full check script.
10. check.py sends real HTTP requests and reads back their actual IDs. It tests changed approvals, wrong owners, malformed input, failures and concurrent duplicate review. Latency is measured around actual requests. Unknown token usage and spend remain null, not fabricated zero. This sequential local sample is not a cloud concurrency benchmark.

## Apply the three pillars to A multi-user AI service deployed from containers

### Latency vs. Cost vs. Quality

Load-test offered vs. completed work, p95 and cost per accepted result at stated concurrency. Autoscaling settings are hypotheses until observed against downstream/GPU limits.

### Deterministic Evaluation

Test readiness against the actual database, restart/readback, isolated restore, denied owner access, overload rejection and a dependency outage on the deployed revision.

### Context Management

Budget resident model memory/KV cache and per-request context separately. Keep tenant/revision-aware application caches; never assume a process-local cache is shared across replicas.

## Failure and deployment work

Separate request concurrency, worker capacity and model/GPU capacity. Add admission control, shared quotas, bounded queues, maximum instances and a documented fallback/stop budget.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
