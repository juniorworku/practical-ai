# Containerize the complete application

## Understand the decision: Containerize the complete application

## Before you begin

Complete sessions 1–18 in this bootcamp. Keep your policy fixtures and evaluation labels in your own workspace. The example below runs independently so a prior missing file cannot block understanding.

## Why this decision matters

A working local Python process is only one part of the release. A complete deployment needs a frontend, API, database, configuration, networking, static assets, startup ordering, and health checks. Container images package code and dependencies; named volumes preserve database data beyond a container’s lifetime.

Keep credentials in runtime configuration. A database port does not need to be public when only the API uses it. Understand the difference between container-local hostnames and browser-visible URLs: the browser cannot resolve a Compose service name. Use a frontend proxy so requests remain on the same origin. Test the built frontend rather than only a development server.

## Vocabulary used in this session

### Container network

A private network where service names resolve for containers, not necessarily for a browser.

### Persistent volume

Storage that survives removal or replacement of a container.

### Readiness probe

A check of the dependency needed for the service to fulfill its readiness claim.

## Worked implementation: Containerize the complete application

## Follow the network and storage boundaries

This file creates every source file for a small DRF/PostgreSQL/Nginx experiment. Inspect the generated files before building. The deliberately plain browser page isolates network and persistence concepts; it is not a replacement for your capstone React interface. The database port stays private, the browser uses relative /api URLs, and Nginx resolves backend on the container network. A PostgreSQL SELECT backs readiness. Named volume lab-data preserves records. Credentials enter at runtime. This unauthenticated, loopback-only synthetic lab uses table creation in the handler solely to remain self-contained; your capstone must use authenticated owner scopes and Django migrations.

### backend/app.py

```python
import os
from django.conf import settings
settings.configure(
    SECRET_KEY=os.environ["DJANGO_SECRET_KEY"], DEBUG=False,
    ALLOWED_HOSTS=["localhost","127.0.0.1","backend"], ROOT_URLCONF=__name__,
    DATABASES={"default":{"ENGINE":"django.db.backends.postgresql", "NAME":os.environ["POSTGRES_DB"],
      "USER":os.environ["POSTGRES_USER"], "PASSWORD":os.environ["POSTGRES_PASSWORD"], "HOST":"db", "PORT":"5432"}},
    INSTALLED_APPS=["rest_framework"],
    REST_FRAMEWORK={"UNAUTHENTICATED_USER":None},
)
import django
django.setup()
from django.db import connection
from django.urls import path
from django.core.wsgi import get_wsgi_application
from rest_framework.decorators import api_view
from rest_framework.response import Response

@api_view(["GET"])
def health(request):
    try:
        with connection.cursor() as cursor:
            cursor.execute("SELECT 1")
            cursor.fetchone()
        return Response({"database":"postgresql","ready":True})
    except Exception:
        return Response({"ready":False,"error":"database_unavailable"},status=503)

@api_view(["GET","POST"])
def drafts(request):
    # Dedicated synthetic local lab only; no authentication or production migration system.
    with connection.cursor() as cursor:
        cursor.execute("CREATE TABLE IF NOT EXISTS lab_drafts(id SERIAL PRIMARY KEY, body TEXT NOT NULL)")
        if request.method=="POST":
            body=request.data.get("body")
            if type(body) is not str or not body.strip() or len(body)>500:
                return Response({"error":"body_required_max_500"},status=400)
            cursor.execute("INSERT INTO lab_drafts(body) VALUES(%s) RETURNING id",[body.strip()])
            return Response({"id":cursor.fetchone()[0],"body":body.strip()},status=201)
        cursor.execute("SELECT id,body FROM lab_drafts ORDER BY id")
        return Response([{"id":row[0],"body":row[1]} for row in cursor.fetchall()])

urlpatterns=[path("api/health/",health),path("api/drafts/",drafts)]
application=get_wsgi_application()
```

### compose.yaml

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: lab
      POSTGRES_USER: lab
      POSTGRES_PASSWORD: ${LAB_DB_PASSWORD:?Set LAB_DB_PASSWORD}
    volumes:
      - lab-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U lab -d lab"]
      interval: 2s
      timeout: 3s
      retries: 30
  backend:
    build: ./backend
    environment:
      POSTGRES_DB: lab
      POSTGRES_USER: lab
      POSTGRES_PASSWORD: ${LAB_DB_PASSWORD:?Set LAB_DB_PASSWORD}
      DJANGO_SECRET_KEY: ${LAB_DJANGO_SECRET:?Set LAB_DJANGO_SECRET}
    depends_on:
      db:
        condition: service_healthy
  frontend:
    build: ./frontend
    ports:
      - "127.0.0.1:${LAB_PORT:-8091}:80"
    depends_on:
      - backend
volumes:
  lab-data:
```

### Run the isolated container experiment

Prerequisite: Docker Engine with Compose available. This is an optional local build; it uses no model key. Save the seven files above under a new `container-lab` folder with exactly the shown paths. Never run this unauthenticated experiment on a public interface or put real content in it. Its static page isolates networking and persistence; keep React for your own capstone.

```sh
cd container-lab
export LAB_DB_PASSWORD=synthetic-local-lab-password
export LAB_DJANGO_SECRET=synthetic-local-lab-secret-for-testing-only
export LAB_PORT=8091
docker compose -p academy-student-lab up -d --build
curl --fail http://127.0.0.1:8091/api/health/
curl --fail -H 'Content-Type: application/json' -d '{"body":"restart-proof-draft"}' http://127.0.0.1:8091/api/drafts/
docker compose -p academy-student-lab up -d --force-recreate backend
curl --fail http://127.0.0.1:8091/api/drafts/
```

Wait for the health request to succeed before the POST; startup ordering alone does not establish HTTP readiness. Open `http://127.0.0.1:8091/` and use the form, then reload. The same saved record must return from the API. Stop only the lab database with `docker compose -p academy-student-lab stop db`; a health request must return HTTP 503. Restart it with `docker compose -p academy-student-lab start db` and repeat readiness/readback. A process can be running while its dependency is unavailable.

Clean up using `docker compose -p academy-student-lab down`. This preserves the named volume. Add `--volumes` only when you deliberately want to delete this lab's synthetic records. Do not substitute your capstone or academy Compose project name.

## Build and challenge your own version

## Worked example

A Compose network contains `frontend`, `backend`, and `db`. Django connects to `db:5432`; the browser connects to `localhost:8080/api/` through Nginx. A health probe should prove the dependency your readiness claim relies on, not just return a hard-coded string.

## Build it yourself

1. Write Dockerfiles and a Compose file for your capstone.
2. Add database readiness, migrations, a non-root application user, and an HTTP health endpoint.
3. Bring up the stack and verify the actual database vendor from the running API container.
4. Restart services and confirm saved synthetic records remain.

## Break it deliberately

Point the API at an unavailable database. The service should fail readiness and expose a useful operational failure rather than advertise healthy persisted behavior.

## Acceptance checks

- The production frontend can call the containerized API.
- A database record survives a service restart.
- No database credential is baked into the image.
