## Why this decision matters

A release plan specifies what you will check, what failure means, and how you will recover. Back up data before applying schema changes. Test a restore into an isolated target rather than assuming a generated backup file is sufficient. A rollback of code does not automatically undo a destructive database migration.

Exercise failure modes deliberately in a local environment: provider unavailable, database restarting, missing static assets, wrong configuration, and oversized requests. Record which data is preserved and which requests must be retried. An operational runbook should let another person diagnose these failures without needing your memory.

## Vocabulary used in this session

### Restore verification

Recovering a backup into an isolated target and checking its actual contents.

### Rollback boundary

Code rollback and data-schema recovery are distinct operations.

### Runbook

Concrete diagnosis and recovery steps that another operator can follow.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
import sqlite3
from tempfile import TemporaryDirectory
from pathlib import Path
with TemporaryDirectory() as folder:
    root = Path(folder)
    source = sqlite3.connect(root/'source.sqlite')
    source.execute('CREATE TABLE drafts(id TEXT PRIMARY KEY, body TEXT)')
    source.execute('INSERT INTO drafts VALUES(?,?)',('d7','reviewed policy draft'))
    source.commit()
    backup = sqlite3.connect(root/'backup.sqlite')
    source.backup(backup)
    backup.close()
    restore = sqlite3.connect(root/'restore.sqlite')
    backup = sqlite3.connect(root/'backup.sqlite')
    backup.backup(restore)
    assert restore.execute('SELECT id,body FROM drafts').fetchall() == [('d7','reviewed policy draft')]
    assert source.execute('SELECT count(*) FROM drafts').fetchone()[0] == 1
    for connection in (source,backup,restore): connection.close()
print('isolated restore verified by representative content; live source unchanged')
```

```text

```

## Walk through the mechanism and its limits

SQLite’s backup API copies a consistent database into another file. A second copy restores it into an isolated target; comparing a representative body checks more than row counts. The original remains unchanged. This is a local recovery mechanism, not a PostgreSQL backup recipe. A production runbook also needs backup age, access, retention, restoration time and acceptable data loss.

## Rehearse the PostgreSQL restore in your previous lab

Return to the isolated `container-lab` from session 19 and start its stack. Save at least one synthetic draft. Keep other writers stopped during this small comparison so source data does not change after the snapshot. Save the entire block below as `verify-restore.sh` and run `sh verify-restore.sh` from that directory. It needs no host PostgreSQL tools: pg_dump, createdb, pg_restore and psql run inside the lab database container.
```sh
set -eu
# Run from the container-lab directory created in session 19.
# Start that isolated stack and save at least one synthetic draft first.
export LAB_DB_PASSWORD=synthetic-local-lab-password
export LAB_DJANGO_SECRET=synthetic-local-lab-secret-for-testing-only
export LAB_PORT=8091
test ! -e lab-backup-review.dump
docker compose -p academy-student-lab exec -T db pg_dump -U lab -d lab --format=custom > lab-backup-review.dump
# createdb stops if this target already exists; never replace the live database.
docker compose -p academy-student-lab exec -T db createdb -U lab lab_restore_review
docker compose -p academy-student-lab exec -T db pg_restore -U lab --no-owner -d lab_restore_review < lab-backup-review.dump
source_rows="$(docker compose -p academy-student-lab exec -T db psql -U lab -d lab -At -v ON_ERROR_STOP=1 -c 'SELECT id,body FROM lab_drafts ORDER BY id')"
restored_rows="$(docker compose -p academy-student-lab exec -T db psql -U lab -d lab_restore_review -At -v ON_ERROR_STOP=1 -c 'SELECT id,body FROM lab_drafts ORDER BY id')"
test -n "$source_rows"
test "$source_rows" = "$restored_rows"
printf '%s\n' 'PASS: isolated PostgreSQL restore matches source IDs and synthetic content'
```

The target database is separate from `lab`. Matching IDs and body text establish that this snapshot can be read after restore, not only that a dump file exists. Save the backup creation time and restore duration. No source writes are replayed after the snapshot; a live service needs a planned consistency and recovery-point strategy. This local synthetic rehearsal does not test encrypted backup custody, retention or disaster recovery. Keep those as explicit operational requirements.
