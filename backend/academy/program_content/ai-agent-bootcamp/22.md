## Why this decision matters

A vertical slice connects a real user action through UI, API, retrieval, draft generation, persistence, and visible result. It is more valuable than six disconnected components that each work alone. Freeze your release scope to the read-only policy assistant and optional fake approval action. Use synthetic data, a fake provider, and your existing evaluation dataset before a live integration.

Keep an evidence bundle as you build. Include the exact setup, observed outputs, tests, source revisions, and failure investigations. A screenshot of a plausible answer cannot prove retrieval correctness or data isolation. Demonstrate those claims through targeted checks and traceable artifacts.

## Vocabulary used in this session

### Vertical slice

One complete user path through interface, API, application logic, storage and visible result.

### Evidence bundle

Inputs, observed outputs, versions, tests and limitations supporting a project claim.

### Offline baseline

A runnable deterministic path requiring no model credentials or network call.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Vertical slice

A vertical slice connects one real user-visible path from input through result and saved readback. It is narrower than many disconnected features. Build normal, clarify, abstain and failure states around the same policy fixtures. The supplied application-layer slice saves a scoped source reference; your final API needs original question and full result as well.

## Step 2 · Evidence bundle

An evidence bundle links each claim to a fixture revision, candidate, actual observation and limitation. A console assertion is evidence for that function call; it does not prove the browser showed a failure correctly. Collect the UI, HTTP and datastore observations needed for each acceptance scenario rather than presenting screenshots as interchangeable proof.

## Step 3 · Offline baseline

An offline baseline uses a fake adapter deliberately to isolate orchestration. It allows repeatable failures and no paid account requirement. Its perfect text echo is not model quality, and a citation ID is not semantic support. Add real-provider comparisons only after the mechanical slice works, retaining the same workload and reviewed acceptance bar.

## Walk through the data and decision

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
import sqlite3
from tempfile import TemporaryDirectory
from pathlib import Path
POLICY = {'id':'returns-v1','text':'Only unopened items within 14 days; opened items excluded.'}
def draft(condition, provider):
    if condition is None: return {'status':'clarify','citations':[]}
    if condition not in {'unopened','opened'}: return {'status':'abstain','citations':[]}
    try: answer = provider(POLICY['text'])
    except TimeoutError: return {'status':'generation_failed','citations':[]}
    return {'status':'needs_review','answer':answer,'citations':[POLICY['id']]}
def offline(text): return text  # Deterministic fake provider, not a trained model.
with TemporaryDirectory() as folder:
    path=Path(folder)/'runs.sqlite'
    db=sqlite3.connect(path)
    db.execute('CREATE TABLE runs(id TEXT,owner TEXT,status TEXT,source TEXT)')
    result=draft('unopened',offline)
    with db: db.execute('INSERT INTO runs VALUES(?,?,?,?)',('r1','acme',result['status'],result['citations'][0]))
    db.close(); db=sqlite3.connect(path)
    assert db.execute('SELECT source FROM runs WHERE id=? AND owner=?',('r1','acme')).fetchone()==('returns-v1',)
    assert db.execute('SELECT source FROM runs WHERE id=? AND owner=?',('r1','other')).fetchone() is None
    assert draft(None,offline)['status']=='clarify'
    assert draft('commercial-contract',offline)['status']=='abstain'
    assert draft('opened',offline)['status']=='needs_review'
    def unavailable(text): raise TimeoutError()
    assert draft('unopened',unavailable)['status']=='generation_failed'
    db.close()
print('offline application slice: draft, clarify, abstain, failure, durable scoped readback')
```

## Walk through the mechanism and its limits

This deliberately small application-layer slice connects policy selection, fake drafting, an explicit status, a source revision and durable owner-scoped readback. It is not a UI/API capstone by itself. The hard-coded condition supports only this synthetic policy, not free-text eligibility reasoning. It gives you a known baseline to connect to your own actual browser and DRF endpoint.

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Completion requires operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to A multi-user AI service deployed from containers

### Latency vs. Cost vs. Quality

Load-test offered vs. completed work, p95 and cost per accepted result at stated concurrency. Autoscaling settings are hypotheses until observed against downstream/GPU limits.

### Deterministic Evaluation

Test readiness against the actual database, restart/readback, isolated restore, denied owner access, overload rejection and a dependency outage on the deployed revision.

### Context Management

Budget resident model memory/KV cache and per-request context separately. Keep tenant/revision-aware application caches; never assume a process-local cache is shared across replicas.

## Failure and deployment work

Separate request concurrency, worker capacity and model/GPU capacity. Add admission control, shared quotas, bounded queues, maximum instances and a documented fallback/stop budget.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
