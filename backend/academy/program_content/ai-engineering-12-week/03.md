# Async Python: bounded work, deadlines and cancellation

## Async Python: bounded work, deadlines and cancellation · concepts and decision

## Before you begin

Python async def creates a coroutine; await suspends it so other work can progress. Review try/finally for cleanup. Use Python3.12 with assertions enabled. All core practice runs offline with the standard library; provider accounts are only for separately labeled integration work.

## The case

Six requests arrive together but the provider contract permits two active calls. One request times out.

## Reason through the decision

Keep at most two active calls, preserve all outcomes and release resources on failure or cancellation.

An async function is cooperative, not automatically bounded. The semaphore caps active provider calls; finally releases accounting on success or failure. gather(return_exceptions=True) keeps every outcome for a batch evaluation; an interactive session may instead cancel siblings on disconnect. Six tasks are safe as a small fixture, but creating a task for every unbounded upload still exhausts memory. Use an admission limit and a bounded queue as well.

## Vocabulary used in this session

### Semaphore

A cap on active concurrent operations, separate from admission capacity.

### Overall deadline

Budget including queue wait, retries and service time.

### Cancellation cleanup

Releasing tasks, connections and accounting when work is abandoned.

## Learn each concept step by step

Read these three explanations before running the specimen. Each connects a definition to the decision it controls.

## Step 1 · Semaphore

A semaphore holds a finite number of permits. async with semaphore waits for a permit and releases it when the block exits, including on exceptions. This caps active service operations; it does not cap the number of waiting tasks. The six-task fixture is finite, while production admission needs a bounded pending queue too.

## Step 2 · Overall deadline

An overall deadline includes time waiting for a semaphore, provider execution and retry delays. Put asyncio.timeout around the entire operation if queue wait must count. An inner HTTP timeout alone starts too late to bound total user waiting. A deadline should produce a recorded timeout outcome rather than silently remove a request from the report.

## Step 3 · Cancellation cleanup

Cancellation is control flow, not an ordinary successful result. A browser disconnect can cancel a task while it is waiting or holding a permit. finally releases your own resources, and the semaphore context releases its permit. After cancel(), await the task or gather it with return_exceptions=True so cleanup actually finishes before checking state.

## Read, run and explain the complete implementation

## Walk through the data and state

1. Six tasks compete for two permits; peak active reaches two.

2. Task 3 raises TimeoutError but its finally block decrements active.

3. gather keeps five results and one exception, and active returns to zero.

## Predict before execution

Save this entire block as example.py in an empty directory. Run `python3 -I example.py` with assertions enabled. It uses only the Python standard library, includes its synthetic data and performs no provider calls. Explain each assertion before running.

```python
import asyncio
async def main():
    active=peak=0
    semaphore=asyncio.Semaphore(2)
    async def generate(index):
        nonlocal active,peak
        async with semaphore:
            active+=1;peak=max(peak,active)
            try:
                await asyncio.sleep(.001)
                if index==3: raise TimeoutError('fixture timeout')
                return ('draft',index)
            finally: active-=1
    outcomes=await asyncio.gather(*(generate(i) for i in range(6)),return_exceptions=True)
    assert peak==2 and active==0
    assert sum(isinstance(x,TimeoutError) for x in outcomes)==1
    assert sum(isinstance(x,tuple) for x in outcomes)==5
    print({'requests':6,'peak_active':peak,'failed':1,'completed':5})
asyncio.run(main())
```
