## The case

A source-grounded chat feature retrieves one wrong passage, correctly abstains once and misses another answer.

## Reason through the decision

Keep no-source and answerable denominators separate; report the missed evidence rather than hiding it as safe abstention.

Retrieval recall needs an explicit denominator. The no-source query has no relevant passage and is scored for correct abstention rather than forcing a 0/0 recall. A correct abstention on unavailable sources and an incorrect abstention caused by retrieval failure are operationally different. This three-case fixture validates scoring; a capstone needs a larger held-out set and factual review.

## Vocabulary used in this session

### Source lifecycle

Received-to-active transitions with failure preservation.

### No-answer evaluation

Testing correct abstention separately from retrieval failure.

### Retrieval/answer separation

Independent scoring of evidence selection and claim quality.

## Learn each concept step by step

Read these three explanations before running the specimen. Each connects a definition to the decision it controls.

## Step 1 · Source lifecycle

The source lifecycle determines which records can be retrieved. received and parsed are not active; activation follows indexing and checks. Keep status visible in the UI and preserve a prior working revision after replacement failure. The capstone should expose this state rather than silently search every uploaded file.

## Step 2 · No-answer evaluation

No-answer evaluation distinguishes a question with no source support from an answerable question whose evidence was missed. Only answerable queries have a relevant-passage recall denominator. Score unsupported questions for the correct abstain/clarify outcome separately, and retain failed retrieval as a failure rather than calling all abstention safe.

## Step 3 · Retrieval/answer separation

Retrieval and answer metrics diagnose different defects. Passage recall@k is |retrieved relevant IDs|/|gold relevant IDs|, averaged over answerable queries. Hit rate only asks whether at least one gold ID appears. With two gold passages and one retrieved, recall is .5 but hit rate is 1. Final claim support must still be reviewed even if recall is perfect.

## Read, run and explain the complete implementation

## Walk through the data and state

1. q1 retrieves its gold p1 within the first two results.

2. q2 has no gold and is evaluated for abstention, not passage recall.

3. q3 misses p3, so mean recall across q1 and q3 is .5.

## Predict before execution

Save this entire block as example.py in an empty directory. Run `python3 -I example.py` with assertions enabled. It uses only the Python standard library, includes its synthetic data and performs no provider calls. Explain each assertion before running.

```python
queries=[{'id':'q1','gold':{'p1'},'ranked':['p2','p1'],'expected':'answer','actual':'answer'},
         {'id':'q2','gold':set(),'ranked':[],'expected':'abstain','actual':'abstain'},
         {'id':'q3','gold':{'p3'},'ranked':['p4'],'expected':'answer','actual':'abstain'}]
answerable=[q for q in queries if q['gold']]
recall=sum(len(set(q['ranked'][:2])&q['gold'])/len(q['gold']) for q in answerable)/len(answerable)
assert recall==.5
assert len(queries)-len(answerable)==1
print({'recall_at_2_answerable':recall,'answerable':2,'no_source_cases':1,'behaviors_correct':2,'all_cases':3})
```

## Failure and deployment work

Quarantine failed parsing, bound upload size and worker queues, activate revisions only after indexing checks, and preserve a working previous revision.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
