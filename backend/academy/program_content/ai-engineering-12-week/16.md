## The case

An allowlisted draft tool receives a private channel ID outside the authenticated actor scope.

## Reason through the decision

Deny at dispatch; tool discovery or a valid JSON argument cannot establish channel permission.

A function schema tells the model how to propose an operation; it does not confer permission. The dispatcher validates allowed fields, authenticated actor scope, types and effects. Real connectors also need least-privilege OAuth scopes, token storage/rotation, retry categories and destination-specific error mapping. Never accept a model-generated user/tenant ID as identity.

## Vocabulary used in this session

### Tool proposal

A model-generated operation that still needs application validation.

### Connector scope

API-granted authority for channels, accounts and actions.

### Draft boundary

Local preparation that does not send or schedule externally.

## Learn each concept step by step

Read these three explanations before running the specimen. Each connects a definition to the decision it controls.

## Step 1 · Tool proposal

Tool binding presents a function name and argument schema so a model can propose a call. The proposal is untrusted data: the application selects the registered function and validates required/extra fields and types. Never eval a function name or run code returned by the model. A schema-valid proposal can still be unauthorized.

## Step 2 · Connector scope

A connector scope is authority granted to an application for an account or resource. Slack channel membership and calendar ownership constrain it further. Bind that grant to server-established actor identity and check destination scope at dispatch. A model-supplied owner or channel cannot expand the authenticated actor’s grants.

## Step 3 · Draft boundary

A draft boundary separates local preparation from external effects. Returning status=draft can be safe without send authority; a send or create operation needs a different dispatcher contract and current approval. Whitelist effect types, rather than assuming every allowed tool is read-only. The optional connector example later supplies actual HTTP methods behind these checks.

## Walk through the data and state

## Predict before execution

Save this entire block as example.py in an empty directory. Run `python3 -I example.py` with assertions enabled. It uses only the Python standard library, includes its synthetic data and performs no provider calls. Explain each assertion before running.

```python
allowed={'draft_reply':{'fields':{'channel','text'},'effect':'local_draft'}}
def dispatch(actor,tool,args):
    contract=allowed.get(tool)
    if not contract or type(args) is not dict or set(args)!=contract['fields']:return 'rejected'
    if args['channel'] not in actor['channels']:return 'denied'
    if not all(type(value) is str for value in args.values()):return 'invalid_type'
    return {'status':'draft','owner':actor['owner'],'text':args['text']}
actor={'owner':'acme','channels':{'support'}}
assert dispatch(actor,'draft_reply',{'channel':'private','text':'hello'})=='denied'
assert dispatch(actor,'send_reply',{'channel':'support','text':'hello'})=='rejected'
assert dispatch(actor,'draft_reply',{'channel':'support','text':'hello'})['status']=='draft'
print('tool schema, application authority and draft-only effect verified')
```
