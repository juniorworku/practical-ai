## Context memory, summaries and cache invalidation · concepts and decision

## The case

## Reason through the decision

Reject the stale memory and test compression against source facts; smaller context is not automatically correct.

Memory is selected application data, not permission to paste all history into every call. A rolling summary can lose exceptions, dates and unresolved decisions; evaluate it against exact source facts and keep recoverable originals. Cached summaries require source/permission invalidation and retention rules. Provider KV/prompt caches and your application memory have different lifecycles.

## Vocabulary used in this session

### Selected memory

Relevant tenant-scoped state rather than the entire conversation.

### Summary fidelity

Preserving conditions, uncertainty and source revision during compression.

### Invalidation trigger

A source, role or prompt change requiring cache/memory refresh.

## Learn each concept step by step

Read these three explanations before running the specimen. Each connects a definition to the decision it controls.

## Step 1 · Selected memory

Selected memory is a bounded subset of durable facts, recent turns and tool results. Choose by owner, permission, relevance and revision before budgeting. Persist originals separately so an omitted condition can be recovered. Pasting every historic message makes context expensive and may reintroduce revoked or stale evidence.

## Step 2 · Summary fidelity

Summary fidelity means preserving what changes a decision: dates, exceptions, scope and uncertainty. “Returns within 14 days” loses the opened-item exclusion, even if it is shorter and fluent. Evaluate compression against source facts and answer cases; token savings alone do not establish useful compression.

## Step 3 · Invalidation trigger

An invalidation trigger changes whether retained content is usable: source revision, membership, prompt/model policy, expiry or retention requirements. A different source revision gives a different cache key in the baseline, but old entries still need permission/retention checks. Application answer caches, conversation memory and provider KV caches are separate objects with different lifecycles.

## Predict before execution

Save this entire block as example.py in an empty directory. Run `python3 -I example.py` with assertions enabled. It uses only the Python standard library, includes its synthetic data and performs no provider calls. Explain each assertion before running.

```python
import hashlib,json
cache={}
def memory(owner,source_revision,question,summary):
    key=hashlib.sha256(json.dumps([owner,source_revision,question]).encode()).hexdigest()
    cache[key]=summary
    return key
first=memory('acme','v1','returns','Unopened within 14 days; opened excluded.')
second=memory('acme','v2','returns','Unopened within 21 days; opened excluded.')
assert first!=second
assert 'opened excluded' in cache[first]
assert first!=memory('other','v1','returns','different tenant')
print('owner/revision memory isolation passed; exception preserved in summary fixture')
```
