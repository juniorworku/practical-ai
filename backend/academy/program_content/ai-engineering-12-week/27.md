## Prompt versioning, CI and critical release gates · concepts and decision

## Before you begin

Session 26: concrete cases and an evaluation report. CI is an automated runner for these checks, not a model-quality oracle. Use Python3.12 with assertions enabled. All core practice runs offline with the standard library; provider accounts are only for separately labeled integration work.

## The case

A candidate improves average quality but fails one unauthorized-action case.

## Reason through the decision

Block promotion, preserve the failure and rerun the relevant regression after fixing its actual cause.

CI needs a reproducible manifest tying code, prompt, model, dataset, parser, context/cache policy and judge to observed results. Separate inexpensive deterministic tests from explicitly budgeted provider evaluations. A 99/100 aggregate cannot waive a critical authorization or unsupported-action failure. Deployment promotion should depend on the relevant gates, not only a green unit-test job.

## Vocabulary used in this session

### Release manifest

A fingerprint of code, prompts, models, data, context and judge revisions.

### Critical gate

A non-negotiable condition independent of aggregate score.

### Budgeted integration job

An explicit CI run with credentials, spending controls and reports.

## Learn each concept step by step

Read these three explanations before running the specimen. Each connects a definition to the decision it controls.

## Step 1 · Release manifest

A release manifest identifies the exact candidate: code, prompt, model, dataset, parser, context/cache policy and judge/rubric revisions. Serialize stable fields and hash them so a change is detectable. A manifest with the same labels but different actual source files is insufficient; use real artifact digests in the integrated pipeline.

## Step 2 · Critical gate

Critical gates cannot be averaged away. One unauthorized effect blocks promotion even if 99 other cases pass. Distinguish a failure from missing evidence: both can block a required gate, but they call for different remediation. Preserve the failing case ID and release fingerprint with the report.

## Step 3 · Budgeted integration job

A budgeted integration job is separate from an offline contract job. Run inexpensive fixture checks on every PR with no provider secrets. Credentialed candidate evaluation uses a trusted environment, a selected test revision, deadlines, request/spend caps and retained artifacts. The full workflow appendix shows the first job and explains the additional candidate boundary.

## Continuous evaluation: complete CI workflow and release boundaries

## Put repeatable checks into CI

Save the complete evaluation_suite.py from session 26 at the root of your own test repository. Save the following workflow as `.github/workflows/evaluation.yaml`. This job has no provider credentials and runs on pull requests. It executes the deterministic contract baseline to check the harness and expected labels, then retains the report even when a check fails. A green job is a harness regression result; it does not certify the candidate model, semantic quality, deployment or scale.

```yaml
name: Evaluation contract regression
on: [push, pull_request]
permissions:
  contents: read
jobs:
  contract-checks:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: '3.12'
      - name: Execute concrete contract cases
        run: python evaluation_suite.py --output fixture-report.json
      - name: Retain case-level evidence
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: contract-evidence
          path: fixture-report.json
          retention-days: 7
```

Record the tested action revisions and pin immutable commit SHAs in your production workflow. Never expose provider or connector secrets to untrusted pull-request code. Add a negative regression test that deliberately changes one critical expected decision: the harness must return a nonzero exit status, retain the failed case and make CI fail. A suite that always turns green cannot establish its gate behavior.

## Candidate evaluation is a separate controlled job

For the actual application, use the harness's HTTP target mode against an authenticated test revision. Start a synthetic application in the job or select a private test deployment by immutable release ID. Keep model/prompt/parser/context/dataset/judge revisions in the report artifact. Set the target token from a protected CI environment, authorize the endpoint and enforce an overall spend/request/deadline limit at the application before running. The harness's four-request semaphore bounds simultaneous attempts, not provider tokens or spend.

Use the exact same held-out cases for baseline and candidate. The required response contract appears in session 26; expected labels stay outside the request. HTTP timeouts, wrong schemas, owner errors and unapproved effects remain failures. Check the intended release ID before interpreting results; evaluating a previous server revision cannot validate a new commit.

The automated report starts with zero semantic reviews. Add a versioned review artifact mapping case IDs to claim-level support, relevance and reviewer/judge disagreement. Mechanical pass rate, reviewed acceptance, critical failures, latency percentiles and all-attempt spend are separate release fields. Block promotion on a critical failure or missing mandatory evidence rather than averaging it away. Retain the old candidate manifest so rollback and subsequent comparison refer to the exact same system.

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Graduation builds toward operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. Early checkpoints assess only boundaries already taught; future deployment controls are planned rather than claimed complete. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to A release candidate tested against normal and edge-case inputs

### Latency vs. Cost vs. Quality

Report latency distributions, total spend, acceptance and critical failures by category. A cheap/fast candidate cannot trade away a mandatory safety or factual-support gate.

### Deterministic Evaluation

Freeze dataset, prompt, model, parser and judge versions. Fail CI on schema/permission regressions; run model-based quality judgments with recorded rubrics and reviewed disagreements.

### Context Management

Compare context sizes and cache policies using the same dataset. Log counts, hit/miss and revision IDs without copying private prompts into traces.

## Failure and deployment work

Trace retries, timeouts and queue wait as separate spans. Redact logs, retain unavailable runs in denominators and rehearse promotion/rollback.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
