## Tracing agent trajectories without leaking prompts · concepts and decision

## Before you begin

Sessions 3 and 20: concurrent work and branch provenance. A trace is a correlated record of stages, timing and outcomes. Use Python3.12 with assertions enabled. All core practice runs offline with the standard library; provider accounts are only for separately labeled integration work.

## The case

Parallel tools each run 800ms; an exporter reports 1600ms wall time and uploads full notes.

## Reason through the decision

Measure actual wall time and retain minimal correlated stage data under an explicit trace retention policy.

A trace explains where time and failures occurred without becoming a copy of confidential prompts. For sequential spans, summing durations can reconstruct elapsed work; parallel spans require a critical-path/wall-time view to avoid double counting. Correlate run IDs with prompt/source revisions and usage, and redact raw provider errors. LangSmith/Phoenix integrations should honor the same payload minimization and retention policy.

## Vocabulary used in this session

### Span

A stage with duration, status and trace correlation.

### Critical path

Wall-time dependency path rather than the sum of parallel work.

### Payload minimization

Logging useful IDs/status without confidential source text.

## Learn each concept step by step

Read these three explanations before running the specimen. Each connects a definition to the decision it controls.

## Step 1 · Span

A span describes one operation with run/span identity, start/end or duration, status and useful revision/usage fields. Include queue wait and retries so “the model was slow” can be distinguished from admission delay. A timeout remains in the trace even when no answer was produced.

## Step 2 · Critical path

The critical path is the dependency path determining wall time. Sequential 20+800+100ms spans sum to 920ms in the baseline. Two 800ms branches starting together instead occupy 800ms, plus orchestration. Record actual timestamps or measured wall time; blindly summing every child span double-counts overlap.

## Step 3 · Payload minimization

Payload minimization logs what is needed to diagnose behavior without copying private prompts/documents. Choose allowlisted keys and stable error categories, then test with a canary secret in input. Redaction after exporting is too late. Trace correlation and retention/access policy are part of the design, not reasons to log everything.

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Graduation builds toward operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. Early checkpoints assess only boundaries already taught; future deployment controls are planned rather than claimed complete. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to A release candidate tested against normal and edge-case inputs

### Latency vs. Cost vs. Quality

Report latency distributions, total spend, acceptance and critical failures by category. A cheap/fast candidate cannot trade away a mandatory safety or factual-support gate.

### Deterministic Evaluation

Freeze dataset, prompt, model, parser and judge versions. Fail CI on schema/permission regressions; run model-based quality judgments with recorded rubrics and reviewed disagreements.

### Context Management

Compare context sizes and cache policies using the same dataset. Log counts, hit/miss and revision IDs without copying private prompts into traces.

## Failure and deployment work

Trace retries, timeouts and queue wait as separate spans. Redact logs, retain unavailable runs in denominators and rehearse promotion/rollback.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
