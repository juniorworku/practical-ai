A production candidate joins interface, API, persistence, provider/local inference, queues, secrets, traces and operational ownership. The local Docker experiment teaches network and storage boundaries; graduating requires applying those boundaries to the full authenticated app. Built frontend behavior, actual database readiness, migrations, restart/readback and an isolated restore are part of release evidence.

Choose a hosting path deliberately. Cloud Run maps request concurrency and instance limits to containerized work; WebSockets still have request timeouts and reconnects may reach a different instance. ECS adds task/service/load-balancer choices, health checks and draining. On either, state and quotas must survive a process and multiple replicas. Keep database connection limits and downstream provider quotas in the capacity plan.

Configured concurrency is not measured hardware capacity. Test offered load, admitted/completed work, failures, queue depth and p95 with quality and spend visible. Increasing a concurrency flag may only create longer waits or GPU memory failures. Maximum instance and budget caps bound potential spend but can force rejection under load. Report the actual tested envelope; a target of thousands of users remains a target until observed under defined conditions.

Self-hosted open models move operations and cost to local/GPU infrastructure. Account for model artifacts/licensing, quantization, resident weights, runtime buffers, KV cache, context length, batching, cold load and monitoring. Ollama provides a local serving route; vLLM serves supported models with batching controls. Compare exact deployed artifacts using the same quality set; neither low marginal API cost nor an OpenAI-compatible shape establishes equivalent behavior.

Rate limits, token reservations, work concurrency and monetary budgets are separate controls. Use shared atomic enforcement across replicas; evaluate limiter-store failure modes and reconciliation of reserved versus observed usage. Hybrid routing must preserve owner/data-residency boundaries and response contracts. A premium fallback is not permission to disclose data approved only for local processing. The final handover includes quality/latency/cost results, 120-case evaluation, context/cache manifest, incident/restore drill, ownership and unresolved blockers. Production readiness is a decision supported by observed evidence, not a certificate issued because a demo deploys.

## Reason through the decision

Use the frontend HTTP proxy and fail dependency-backed readiness; keep PostgreSQL private with persistent storage.

Images package code; volumes or managed stores preserve state. A browser cannot use Docker service DNS directly. A same-origin proxy separates browser routing from internal service names. Readiness must query the dependency needed to serve work; a hard-coded healthy response can mask a missing database. Runtime credentials belong outside built layers and source control.

## Vocabulary used in this session

### Runtime configuration

Credentials and environment supplied outside built image layers.

### Dependency readiness

A probe verifying the service can use the required datastore.

### Durable readback

A saved server record returned after replacement/restart.

## Learn each concept step by step

Read these three explanations before running the specimen. Each connects a definition to the decision it controls.

## Step 1 · Runtime configuration

Runtime configuration supplies credentials and environment after image creation. A Docker image contains application code/dependencies; a secret baked into a layer remains extractable even if later deleted. Use runtime secret injection and keep the database on the private container network. Browser JavaScript must use an HTTP API rather than database credentials.

## Step 2 · Dependency readiness

Dependency readiness answers whether the application can serve its required work now. Query the actual datastore and return unavailable when it is down. A process-alive endpoint can be useful for liveness, but it is not the same claim. A browser cannot resolve the Docker service name db; the same-origin proxy can resolve backend on the internal network.

## Step 3 · Durable readback

Durable readback proves a write survived the relevant boundary. Save a synthetic record through the API, replace the backend container, read it again, then rehearse backup restore into an isolated database. A named volume preserves bytes but does not prove a backup restores correctly. Owner authorization is another application check, absent from the deliberately small unauthenticated network lab.

### backend/app.py

```python
import os
from django.conf import settings
settings.configure(
    SECRET_KEY=os.environ["DJANGO_SECRET_KEY"], DEBUG=False,
    ALLOWED_HOSTS=["localhost","127.0.0.1","backend"], ROOT_URLCONF=__name__,
    DATABASES={"default":{"ENGINE":"django.db.backends.postgresql", "NAME":os.environ["POSTGRES_DB"],
      "USER":os.environ["POSTGRES_USER"], "PASSWORD":os.environ["POSTGRES_PASSWORD"], "HOST":"db", "PORT":"5432"}},
    INSTALLED_APPS=["rest_framework"],
    REST_FRAMEWORK={"UNAUTHENTICATED_USER":None},
)
import django
django.setup()
from django.db import connection
from django.urls import path
from django.core.wsgi import get_wsgi_application
from rest_framework.decorators import api_view
from rest_framework.response import Response

@api_view(["GET"])
def health(request):
    try:
        with connection.cursor() as cursor:
            cursor.execute("SELECT 1")
            cursor.fetchone()
        return Response({"database":"postgresql","ready":True})
    except Exception:
        return Response({"ready":False,"error":"database_unavailable"},status=503)

@api_view(["GET","POST"])
def drafts(request):
    # Dedicated synthetic local lab only; no authentication or production migration system.
    with connection.cursor() as cursor:
        cursor.execute("CREATE TABLE IF NOT EXISTS lab_drafts(id SERIAL PRIMARY KEY, body TEXT NOT NULL)")
        if request.method=="POST":
            body=request.data.get("body")
            if type(body) is not str or not body.strip() or len(body)>500:
                return Response({"error":"body_required_max_500"},status=400)
            cursor.execute("INSERT INTO lab_drafts(body) VALUES(%s) RETURNING id",[body.strip()])
            return Response({"id":cursor.fetchone()[0],"body":body.strip()},status=201)
        cursor.execute("SELECT id,body FROM lab_drafts ORDER BY id")
        return Response([{"id":row[0],"body":row[1]} for row in cursor.fetchall()])

urlpatterns=[path("api/health/",health),path("api/drafts/",drafts)]
application=get_wsgi_application()
```

### Isolated restore drill

Save this complete shell script as restore-drill.sh and run `sh restore-drill.sh` from that lab directory while its stack is healthy. It restores synthetic records into a separate named test database, verifies readback without modifying the source database. The script retains the isolated restore database and backup for inspection; remove only those named lab artifacts when finished.

```sh
set -eu
# Run from the container-lab directory created in session 19.
# Start that isolated stack and save at least one synthetic draft first.
export LAB_DB_PASSWORD=synthetic-local-lab-password
export LAB_DJANGO_SECRET=synthetic-local-lab-secret-for-testing-only
export LAB_PORT=8091
test ! -e lab-backup-review.dump
docker compose -p academy-student-lab exec -T db pg_dump -U lab -d lab --format=custom > lab-backup-review.dump
# createdb stops if this target already exists; never replace the live database.
docker compose -p academy-student-lab exec -T db createdb -U lab lab_restore_review
docker compose -p academy-student-lab exec -T db pg_restore -U lab --no-owner -d lab_restore_review < lab-backup-review.dump
source_rows="$(docker compose -p academy-student-lab exec -T db psql -U lab -d lab -At -v ON_ERROR_STOP=1 -c 'SELECT id,body FROM lab_drafts ORDER BY id')"
restored_rows="$(docker compose -p academy-student-lab exec -T db psql -U lab -d lab_restore_review -At -v ON_ERROR_STOP=1 -c 'SELECT id,body FROM lab_drafts ORDER BY id')"
test -n "$source_rows"
test "$source_rows" = "$restored_rows"
printf '%s\n' 'PASS: isolated PostgreSQL restore matches source IDs and synthetic content'
```

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Completion requires operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to A multi-user AI service deployed from containers

### Latency vs. Cost vs. Quality

Load-test offered vs. completed work, p95 and cost per accepted result at stated concurrency. Autoscaling settings are hypotheses until observed against downstream/GPU limits.

### Deterministic Evaluation

Test readiness against the actual database, restart/readback, isolated restore, denied owner access, overload rejection and a dependency outage on the deployed revision.

### Context Management

Budget resident model memory/KV cache and per-request context separately. Keep tenant/revision-aware application caches; never assume a process-local cache is shared across replicas.

## Failure and deployment work

Separate request concurrency, worker capacity and model/GPU capacity. Add admission control, shared quotas, bounded queues, maximum instances and a documented fallback/stop budget.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
