## Vocabulary used in this session

### Route selection

A measured decision about which model handles a particular task.

### Residency boundary

Where approved data may be processed, independent of model availability.

### Comparable workload

The same labeled inputs and conditions across candidate routes.

## Learn each concept step by step

Read these three explanations before running the specimen. Each connects a definition to the decision it controls.

## Step 1 · Route selection

Route selection maps a request to an allowed execution path. The baseline uses supplied routine/complex labels, so it tests routing logic rather than a difficulty classifier. Unknown tasks go to review. To claim intelligent routing quality, independently label difficulty and compare route choices/output acceptance on held-out requests.

## Step 2 · Residency boundary

A residency boundary specifies where approved data may be processed. A premium cloud endpoint is not allowed for local-only material merely because a local model failed or ran out of context. Check data policy before selecting an adapter or cache, and keep the same owner/source revisions across paths.

## Step 3 · Comparable workload

Comparable workloads keep inputs, relevance labels, acceptance standards and measurement conditions fixed across all-local, all-premium and hybrid candidates. Include retries, fallback calls and review effort. A hybrid system can reduce one cost while raising tail latency or errors; a selected route is not itself a measured advantage.

requests=[{'id':'q1','kind':'routine','owner':'acme'}, {'id':'q2','kind':'complex','owner':'acme'}, {'id':'q3','kind':'unknown','owner':'acme'}]
def route(request,budget):
    if budget<=0:return 'budget_exhausted'
    if request['kind']=='routine':return 'local'
    if request['kind']=='complex':return 'premium'
    return 'review'
assert [route(r,10) for r in requests]==['local','premium','review']
assert route(requests[0],0)=='budget_exhausted'

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Completion requires operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to A multi-user AI service deployed from containers

### Latency vs. Cost vs. Quality

Load-test offered vs. completed work, p95 and cost per accepted result at stated concurrency. Autoscaling settings are hypotheses until observed against downstream/GPU limits.

### Deterministic Evaluation

Test readiness against the actual database, restart/readback, isolated restore, denied owner access, overload rejection and a dependency outage on the deployed revision.

### Context Management

Budget resident model memory/KV cache and per-request context separately. Keep tenant/revision-aware application caches; never assume a process-local cache is shared across replicas.

## Failure and deployment work

Separate request concurrency, worker capacity and model/GPU capacity. Add admission control, shared quotas, bounded queues, maximum instances and a documented fallback/stop budget.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
