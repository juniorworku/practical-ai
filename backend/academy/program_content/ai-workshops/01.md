## Understand the decision: Model the document before automating it

## Before you begin

## Why this decision matters

Document extraction is a data-modeling problem before it is a prompting problem. Decide which fields are required, which may be unknown, and which need review. A missing field, a zero value, and an unreadable field are different states. Preserve a link to the source excerpt so a reviewer can audit each extracted value.

Start with synthetic purchase requests rather than private invoices. Define currencies and dates explicitly. A model should not invent a due date because the schema requires one. If an external action depends on a value, validate it independently and require review when uncertainty changes the decision. Your output is a draft record, not an approved purchase.

## Vocabulary used in this session

### Extraction schema

A definition of fields, allowed types, unknown states and review requirements.

### Unknown value

A field the source does not establish, distinct from zero or a guessed default.

### Evidence span

The source text supporting a particular extracted field.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Extraction schema

An extraction schema describes fields, types, whether unknown is allowed and where the supporting text lives. Start from the document’s decisions, not a prompt asking for everything. Quantity and unit price can be known while currency remains unknown. Requiring a key means the key must be present; it does not authorize inventing its value.

## Step 2 · Unknown value

Unknown differs from zero, empty and contradictory. Zero may be a real observed quantity, null may mean absent evidence, and two competing amendments need conflict review. Preserve these states until a documented rule or reviewer resolves them. A default currency can make downstream totals look valid while changing the meaning of the source.

## Step 3 · Evidence span

An evidence span links the extracted value to the exact source revision and location. A substring check establishes the text appears, not that you interpreted its role correctly. “Previous quantity 2, now 3” contains both numbers. Retain the original and amendment with their roles before selecting an active value.

## Worked implementation: Model the document before automating it

## Walk through the data and decision

1. The source supplies quantity and price but no currency or due date.

2. Each recorded span appears literally in the source.

3. Missing currency/date remain None and create review reasons rather than fabricated defaults.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
source = 'Order 2 seats at 12.50 each.'
record = {'quantity':2,'unit_price':'12.50','currency':None,'due_date':None,
          'evidence':{'quantity':'2 seats','unit_price':'12.50 each'},
          'review_reasons':['currency absent','due date absent']}
assert all(span in source for span in record['evidence'].values())
assert record['currency'] is None and record['due_date'] is None
assert record['review_reasons']
print(record)
```

## Walk through the mechanism and its limits

The record is manually labeled, not extracted by a model. It establishes a schema and an answer sheet before automation. Evidence spans point to exact text; nullable values represent absent facts rather than zero or a guessed default. Span membership is only a first check: an old quoted price may also occur in the source without being the current price.

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Graduation builds toward operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. Early checkpoints assess only boundaries already taught; future deployment controls are planned rather than claimed complete. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to purchase-request extraction

### Latency vs. Cost vs. Quality

Measure time to first output and total completion separately. Compare retry cost and accepted-output rate under a fixed overall deadline.

### Deterministic Evaluation

Fake 429, 503, permission failure, malformed JSON, cancellation and a partial stream. Assert bounded retry and no false saved/success status.

### Context Management

Track actual input/output usage when supplied; include retry usage. Key caches by owner, model, prompt and source revisions; never cache partial streams as complete answers.

## Failure and deployment work

Honor Retry-After within the total budget, stop sibling tasks on disconnect, and separate safe draft retries from uncertain external writes.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
