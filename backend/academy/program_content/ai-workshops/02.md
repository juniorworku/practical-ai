# Build a validated extraction pipeline

## The engineering or business decision

Separate extraction, normalization, validation, and review. Extraction identifies candidate values; normalization converts formats; validation checks consistency; review resolves uncertainty. Keeping stages distinct lets you diagnose whether a wrong total came from reading the document or from arithmetic.

Use decimal arithmetic for money-like values and do not let generated text perform authoritative calculations. Validate types and ranges before downstream use. Keep the raw field beside the normalized field so parsing decisions remain inspectable. A fake extraction adapter makes this pipeline testable offline, while a later real provider can be compared using the same fixtures.

## Worked example

An extracted request has quantity `12`, unit price `25.00`, and total `250.00`. Deterministic validation computes `300.00` and flags the mismatch. A fluent model explanation cannot resolve that contradiction. The record goes to review with the original values preserved.

## Build it yourself

1. Use the downloadable `extraction` lab to implement required-field and total-consistency checks.
2. Create normalizers for the date and amount formats you explicitly support.
3. Build a review report listing field, raw value, normalized value, and failure reason.
4. Add tests for negative quantity, missing currency, malformed numbers, and mismatched totals.

## Break it deliberately

An input uses a comma as either a thousands separator or decimal mark. Reject ambiguity unless the source format is known and documented.

## Acceptance checks

- Arithmetic runs in deterministic code.
- Invalid records are quarantined with reasons.
- Tests use all original fixtures, including conflicting values.
