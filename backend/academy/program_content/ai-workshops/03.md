## Why this decision matters

An extraction system succeeds when a person can efficiently identify and correct errors. Measure field accuracy separately from record readiness: nine correct fields do not make a record safe if the bank reference is wrong. Track corrections and the reason a record needed review.

Evaluate using the same labeled documents before and after a change. Report missing-field handling, false acceptance, review burden, and time spent checking source evidence. Do not claim time savings based only on model response latency. Human review and exception handling are part of the workflow cost.

## Vocabulary used in this session

### Field accuracy

Correctness measured for individual extracted fields.

### False acceptance

An incorrect record passes the readiness gate.

### Review burden

Human source inspection, correction and exception work required by the workflow.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Field accuracy

Field accuracy measures correctly extracted fields over labeled fields, but records can still be unusable when one critical value is wrong. Compute both field and whole-record outcomes against the same reviewed inputs. Report the scoring rule for unknown values; do not count a convenient blank as correct without a gold annotation.

## Step 2 · False acceptance

False acceptance means a wrong record passed the gate. Distinguish its count, rate among accepted records and rate among all attempts. One wrong payment reference can matter more than several correct low-risk fields. A high field average does not compensate for accepting a consequential error; make critical-field policy explicit.

## Step 3 · Review burden

Review burden includes time spent on accepted outputs, flagged exceptions and corrections. A gate that sends everything to review can remove automatic errors while eliminating the expected benefit. Compare candidate gates on identical inputs, retaining review minutes and correct records needlessly held for review. Choose the error-cost policy before declaring a winner.

```python
# Manually labeled record correctness and gate outcomes for the same four inputs.
rows = [
 {'id':'d1','correct_fields':3,'fields':3,'record_correct':True,'accepted':True,'review_minutes':1},
 {'id':'d2','correct_fields':2,'fields':3,'record_correct':False,'accepted':True,'review_minutes':1},
 {'id':'d3','correct_fields':2,'fields':3,'record_correct':False,'accepted':False,'review_minutes':4},
 {'id':'d4','correct_fields':3,'fields':3,'record_correct':True,'accepted':False,'review_minutes':3},
]
field_accuracy=sum(r['correct_fields'] for r in rows)/sum(r['fields'] for r in rows)
false_accepted=sum(r['accepted'] and not r['record_correct'] for r in rows)
accepted=sum(r['accepted'] for r in rows)
assert false_accepted==1 and accepted==2
print({'field_accuracy':round(field_accuracy,3),'false_accepted':false_accepted,
       'accepted':accepted,'records':len(rows),'review_minutes':sum(r['review_minutes'] for r in rows)})
```

## Walk through the mechanism and its limits

Field accuracy is 10/12, but one of two accepted records is wrong. The accepted-error fraction is 1/2; the population false-acceptance fraction is 1/4. Always name the denominator. The correctly extracted d4 still costs review time because the gate is conservative. These trade-offs require observed review work, not only parser response time.

## Apply the three pillars to purchase-request extraction

### Latency vs. Cost vs. Quality

Measure time to first output and total completion separately. Compare retry cost and accepted-output rate under a fixed overall deadline.

### Deterministic Evaluation

Fake 429, 503, permission failure, malformed JSON, cancellation and a partial stream. Assert bounded retry and no false saved/success status.

### Context Management

Track actual input/output usage when supplied; include retry usage. Key caches by owner, model, prompt and source revisions; never cache partial streams as complete answers.

## Failure and deployment work

Honor Retry-After within the total budget, stop sibling tasks on disconnect, and separate safe draft retries from uncertain external writes.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
