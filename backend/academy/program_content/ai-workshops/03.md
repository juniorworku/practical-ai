# Review queues and extraction evaluation

## The engineering or business decision

An extraction system succeeds when a person can efficiently identify and correct errors. Measure field accuracy separately from record readiness: nine correct fields do not make a record safe if the bank reference is wrong. Track corrections and the reason a record needed review.

Evaluate using the same labeled documents before and after a change. Report missing-field handling, false acceptance, review burden, and time spent checking source evidence. Do not claim time savings based only on model response latency. Human review and exception handling are part of the workflow cost.

## Worked example

Version A extracts eight of ten records completely but accepts one wrong total. Version B extracts seven completely and sends three to review, with no false acceptance in this sample. The correct trade-off depends on the cost of a bad accepted record and the available reviewer capacity.

## Build it yourself

1. Build a simple review table with editable draft values and a source excerpt.
2. Compare your outputs with labels, classifying errors by field and failure type.
3. Time a manual review of all ten records and compare it with the original baseline.
4. Write an operating note stating supported document formats and escalation rules.

## Break it deliberately

Hide an extraction error in a record with high aggregate accuracy. Your readiness check should still block acceptance of that specific record.

## Acceptance checks

- Field accuracy and false acceptance are reported separately.
- The reviewer can trace a correction to source evidence.
- The report includes human checking time.
