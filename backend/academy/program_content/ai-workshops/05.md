## Why this decision matters

An action register is durable structured state, not just a generated summary. Assign stable IDs to draft actions and preserve the transcript revision that produced them. When a transcript changes, identify which actions need review rather than blindly appending duplicates.

Confirmation should bind to a specific version of an action. If the due date or owner changes after confirmation, reopen review. Notifications and task-system writes are external actions: keep them disabled in this studio and export a reviewed local file instead. A fake destination lets you test formatting and duplicates without contacting anyone.

## Vocabulary used in this session

### Action revision

A particular version of action fields and supporting transcript identity.

### Confirmation

Human review bound to a specific draft action revision.

### Stale save

An older edit that conflicts with a newer saved revision.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Action revision

An action revision identifies exactly which owner, date and wording are being reviewed. Stable transcript/action identity avoids creating duplicate work on reprocessing. Editing a record increments its version; retaining an old approved boolean would make the new contents look confirmed. Preserve correction history alongside the current value.

## Step 2 · Confirmation

Confirmation binds a human decision to a specific revision. Only confirmed==version is exportable in the fixture. A confirmed version two must not approve version three. Recheck the revision at the confirmation action itself, not just when the screen first loaded, because another editor may have saved in between.

## Step 3 · Stale save

A stale save uses an expected version older than the current one. Reject it rather than overwriting a colleague’s correction. The user should see a conflict and retain their unsaved input for comparison. The in-memory fixture teaches the invariant; durable storage and actual HTTP conflict behavior belong in the integrated studio.

## Walk through the data and decision

1. Repeated ingest of the same transcript/action returns the existing row.

2. Editing version 1 creates version 2 and invalidates confirmation.

3. After version 2 export, editing to version 3 clears confirmation again.

```python
import csv, io
register={}
def ingest(transcript, action, owner):
    key=(transcript,action)
    if key not in register: register[key]={'id':action,'owner':owner,'version':1,'confirmed':None}
    return register[key]
def edit(row, expected, owner):
    if row['version']!=expected: return 'conflict'
    row.update(owner=owner,version=expected+1,confirmed=None)
    return 'saved'
row=ingest('m3-v1','a2','Amina')
assert ingest('m3-v1','a2','Amina') is row
assert edit(row,1,'David')=='saved'
row['confirmed']=row['version']
assert edit(row,1,'Sam')=='conflict'
buffer=io.StringIO(); writer=csv.writer(buffer); writer.writerow(['id','owner','version'])
for value in register.values():
    if value['confirmed']==value['version']: writer.writerow([value['id'],value['owner'],value['version']])
assert list(csv.reader(io.StringIO(buffer.getvalue())))[1]==['a2','David','2']
assert edit(row,2,'Amina')=='saved' and row['confirmed'] is None
print('one action; revision 2 exported; revision 3 requires confirmation')
```

## Walk through the mechanism and its limits

Stable transcript/action identity deduplicates replay of the same annotated action. An edit consumes an expected version and clears confirmation. Export includes only the exact confirmed version. The in-memory store demonstrates transition semantics, not durability or concurrent safety. A new transcript revision requires reconciliation of action identity; simply generating a new key could create duplicate commitments.
