# Build an action register with human confirmation

## The engineering or business decision

An action register is durable structured state, not just a generated summary. Assign stable IDs to draft actions and preserve the transcript revision that produced them. When a transcript changes, identify which actions need review rather than blindly appending duplicates.

Confirmation should bind to a specific version of an action. If the due date or owner changes after confirmation, reopen review. Notifications and task-system writes are external actions: keep them disabled in this studio and export a reviewed local file instead. A fake destination lets you test formatting and duplicates without contacting anyone.

## Worked example

Action `M03-A02` is “Prepare accessibility checklist,” proposed owner Amina, due Friday. The reviewer changes the owner to David and confirms revision 2. An older browser tab submitting revision 1 must receive a conflict instead of replacing the correction.

## Build it yourself

1. Implement a local action register with stable IDs, version, proposed fields, and confirmation state.
2. Build a review form or spreadsheet that records corrections.
3. Create a local CSV export of confirmed actions only.
4. Simulate two edits to the same action and detect a stale save.

## Break it deliberately

Reprocess the same transcript twice. Confirm that it does not create two approved tasks for one commitment.

## Acceptance checks

- Only confirmed records appear in the export.
- Duplicate processing is identified.
- A stale edit cannot overwrite a newer confirmed action.
