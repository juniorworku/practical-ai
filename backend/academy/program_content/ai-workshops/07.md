## Understand the decision: Form a question and an evidence plan

## Before you begin

This is studio 3. Begin with basic Python functions, dictionaries and assertions; the specimen below supplies all its data. No other academy program or paid model account is required.

## Why this decision matters

Research automation needs a question that can be answered from identifiable evidence. Define the decision you are supporting, inclusion rules, publication-date limits, and what would count as contradictory information. A list of links is not a synthesis, and a model’s familiarity with a topic is not source verification.

Choose a low-stakes product or technical comparison with public sources. Prefer primary documentation for factual claims. Record when you accessed a page and whether the information describes an announced feature, an available feature, or an observed behavior. Avoid copying entire copyrighted articles into your project; preserve short relevant evidence notes and source links.

## Vocabulary used in this session

### Decision question

A scoped question whose answer helps someone choose an action or option.

### Inclusion rule

A criterion determining which evidence is relevant to the comparison.

### Evidence provenance

Source identity, access date, scope and support for a recorded claim.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Decision question

A decision question states a choice and criteria that could change it: which parser preserves the approved inputs while operating offline? “Research AI tools” has no stopping condition. Declare hard constraints and acceptable evidence before searching so attractive marketing does not redefine the task after the fact.

## Step 2 · Inclusion rule

An inclusion rule decides which source statements belong in the evidence table. Keep documented features, measured tests and promotional claims separate. Conflicting statements can describe different modes or versions. Do not count votes; record the conflict and ask what observation would resolve the specific operational requirement.

## Step 3 · Evidence provenance

Evidence provenance records publisher, document version, access date, relevant excerpt and test environment where applicable. A successful offline run supports that version and mode on those inputs, not every product configuration. Missing license evidence remains unknown. This studio uses synthetic source notes before students investigate real candidates.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
criteria={'offline':'must run with network disabled','utf8':'must preserve accented text','license':'must have documented permitted use'}
evidence=[{'id':'e1','criterion':'offline','kind':'marketing','value':'yes','scope':'advertised'},
          {'id':'e2','criterion':'offline','kind':'technical_note','value':'requires remote API','scope':'default mode'}]
def assessment(criterion):
    rows=[r for r in evidence if r['criterion']==criterion]
    values={r['value'] for r in rows}
    if not rows: return 'unknown'
    return 'conflict_requires_resolution' if len(values)>1 else 'documented_claim_needs_scope_check'
assert assessment('offline')=='conflict_requires_resolution'
assert assessment('license')=='unknown'
print({'offline':assessment('offline'),'license':assessment('license')})
```

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Graduation builds toward operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. Early checkpoints assess only boundaries already taught; future deployment controls are planned rather than claimed complete. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to a claim-and-citation research notebook

### Latency vs. Cost vs. Quality

Compare citation coverage, unresolved claims, review time and retrieval latency on the same research questions.

### Deterministic Evaluation

Assert citation IDs exist and belong to the selected research set; review claim support separately from mechanical citation validity.

### Context Management

Keep bounded excerpts and provenance; conflicting or missing sources must remain visible instead of being summarized away.

## Failure and deployment work

Bound source fetching and extraction, record unavailable sources, and keep an honest incomplete research result for review.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
