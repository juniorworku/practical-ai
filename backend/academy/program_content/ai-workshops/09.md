# Run a small benchmark and write a decision memo

## The engineering or business decision

A benchmark is only meaningful when candidates receive comparable inputs, settings, and measurement rules. Define the dataset and scoring before running it. Record environment and version information. A tiny benchmark is useful for a local decision, but it does not establish universal superiority.

Combine observed results with documented constraints. If one tool performs better but cannot run in your required environment, that constraint matters. Explain how weights or missing evidence affect the decision. Your reader should be able to disagree with a weight and see how the conclusion changes.

## Worked example

Three parsers process the same five synthetic documents. Measure successful extraction, formatting preservation, and elapsed time. A parser that fails one format is recorded as a failure for that input, not excluded from the average. The memo states that five examples are an initial feasibility check.

## Build it yourself

1. Design five representative synthetic inputs and a scoring sheet.
2. Run the feasible candidates yourself, preserving raw outputs and versions.
3. Build a decision table that separates measured results, documentation, and unknowns.
4. Write a one-page recommendation with conditions that would change it.

## Break it deliberately

Increase the weight of offline operation. Recompute the ranking and explain whether the preferred option changes.

## Acceptance checks

- Candidate comparisons use the same inputs.
- Failed runs stay in the result set.
- The recommendation includes scope and sensitivity to priorities.
