## Understand the decision: Routing rules, confusion matrices, and fallback

## Before you begin

## Why this decision matters

A confusion matrix shows which categories are being mistaken for which others. Overall accuracy can hide a dangerous pattern when one category is rare. Establish a deterministic baseline first, then compare a model-based or hybrid classifier against the same labeled messages.

Fallback behavior is part of the classifier. Unknown outputs should not become a default operational action. A valid category string still needs permission checks before any write occurs. Keep automatic actions disabled in this project; the result is a suggested queue and explanation using observable features or evidence, followed by human review.

## Vocabulary used in this session

### Confusion matrix

Counts showing which expected categories were predicted as which other categories.

### Per-class recall

The share of true examples of a category correctly identified.

### Fallback route

An explicit review behavior for uncertainty, invalid labels or unavailable classifiers.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Confusion matrix

A confusion matrix places expected classes on rows and predicted classes on columns in this lesson. Each attempt increments one cell. Write that orientation beside the table; reversing it exchanges precision and recall. An unknown model label must map to a documented fallback rather than silently creating an unauthorized workflow state.

## Step 2 · Per-class recall

Per-class recall is correct predictions of that class divided by actual examples of it. Precision divides by predictions of it. An overall accuracy score can hide a classifier that never detects a rare critical class. Report class support and undefined denominators explicitly; no expected review cases means review recall is unknown, not perfect.

## Step 3 · Fallback route

A fallback route keeps uncertain or invalid predictions reviewable without claiming correct automatic classification. Review capacity has a cost and must be measured. Compare a majority-only baseline on the same imbalanced examples, then inspect missed minority work and the next allowed action. A routing failure must not become an effect authorization.

## Count missing predictions in a per-class routing report

## Before this studio

Sessions 10–11: a fixed taxonomy, uncertainty route, confusion matrix and per-class recall. A dictionary maps stable case IDs to the actual predictions.

## Step 1 · Define the unit before calculating

One row is one attempted case with one independently assigned gold route. Stable IDs join the predictions to that case table. Duplicate case IDs are invalid; extra prediction IDs are invalid because they would change the population. This fixture uses billing and technical, with review as an allowed fallback. Missing predictions are retained, not silently removed by iterating only returned results.

## Step 2 · Construct counts from actual decisions

The matrix key is (gold, prediction). Every attempted case increments one cell. A missing result becomes review and also increments the separate missing count, preserving the difference between an intentional uncertainty route and a failed response. An unknown label is a schema error rather than an invented new category. In a real service, capture whether the missing response was a timeout, parsing failure or unavailable dependency.

## Step 3 · Calculate recall using the gold population

For billing, one correct prediction out of two gold billing rows gives .5 recall; the misrouted billing row remains in the denominator. Technical also has one correct out of two, even though one prediction is absent. A class with no gold cases has undefined recall, represented by None, rather than a perfect 1.0. This small report is not a calibrated confidence estimate or an estimate of real customer traffic.

## Step 4 · Compare changes without hiding regressions

The result is 2 correct of 4 attempted, with one missing prediction. Before changing a rule, freeze this table and add a separate development case. Compare each class as well as total correct. Routing every uncertain case to review may reduce false automatic routes while increasing human workload. Record both consequences; a lower automated error count alone does not establish a better operational system.

## Complete worked example

Save this entire block as example.py in a fresh directory. Run `python3.12 -I example.py` with assertions enabled. All imports are included; no account, provider call or other course is required.

```python
"""A missing prediction remains a routing failure, not a dropped row."""
def report(cases, predictions):
    if len({row['id'] for row in cases}) != len(cases):
        raise ValueError('duplicate case')
    labels = {'billing', 'technical'}
    if any(row['gold'] not in labels for row in cases):
        raise ValueError('unknown gold label')
    ids = {row['id'] for row in cases}
    if set(predictions) - ids:
        raise ValueError('prediction without case')
    matrix = {(gold, pred): 0 for gold in labels for pred in labels | {'review'}}
    missing = 0
    for row in cases:
        prediction = predictions.get(row['id'])
        if prediction is None:
            missing += 1
            prediction = 'review'
        if prediction not in labels | {'review'}:
            raise ValueError('unknown prediction')
        matrix[row['gold'], prediction] += 1
    recall = {}
    for label in sorted(labels):
        total = sum(value for (gold, _), value in matrix.items() if gold == label)
        recall[label] = matrix[label, label] / total if total else None
    return {'attempted': len(cases), 'missing': missing, 'recall': recall,
            'correct': sum(matrix[label, label] for label in labels)}

cases = [{'id': 'a', 'gold': 'billing'}, {'id': 'b', 'gold': 'billing'},
         {'id': 'c', 'gold': 'technical'}, {'id': 'd', 'gold': 'technical'}]
result = report(cases, {'a': 'billing', 'b': 'technical', 'c': 'technical'})
assert result == {'attempted': 4, 'missing': 1,
                  'recall': {'billing': .5, 'technical': .5}, 'correct': 2}
print('4 attempted, 2 correct; missing prediction retained; recall .5 for each class')
```
