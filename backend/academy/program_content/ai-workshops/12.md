# Connect triage to a reviewable work queue

## The engineering or business decision

Routing becomes operationally useful when the queue preserves message identity, prediction revision, review state, and correction history. Do not overwrite the original message with a cleaned summary. Duplicate inbound events should not create duplicate work items, and replaying an event should remain traceable.

Reviewers need to know why a suggestion is unresolved, but a model’s confident explanation is not proof. Show the category definition and source message. Record corrections so you can later expand the evaluation set. Separate experimentation on historical synthetic messages from changes to a live queue.

## Worked example

Message `ticket-017` enters once and receives a suggested topic. A second delivery with the same event ID updates the delivery log but does not create a second work item. A reviewer changes the topic; the correction stores both the old and new values with the classifier revision.

## Build it yourself

1. Build a local queue with suggested, reviewed, and unresolved states.
2. Use a stable inbound event ID to detect duplicate delivery.
3. Add reviewer correction history and export corrected examples for evaluation.
4. Demonstrate replay, duplicate events, and a classifier outage without data loss.

## Break it deliberately

Two reviewers change the same item. Detect or serialize the conflict so the audit history reflects what actually happened.

## Acceptance checks

- Duplicate events do not duplicate work.
- Original messages and corrections remain distinct.
- Outages retain queued inputs for later review.
