## Why this decision matters

Routing becomes operationally useful when the queue preserves message identity, prediction revision, review state, and correction history. Do not overwrite the original message with a cleaned summary. Duplicate inbound events should not create duplicate work items, and replaying an event should remain traceable.

Reviewers need to know why a suggestion is unresolved, but a model’s confident explanation is not proof. Show the category definition and source message. Record corrections so you can later expand the evaluation set. Separate experimentation on historical synthetic messages from changes to a live queue.

## Vocabulary used in this session

### Inbound event ID

A stable identifier used to recognize repeated delivery of the same input.

### Correction history

A record of old and new labels, reviewer and classifier revision.

### Queue state

A durable stage such as suggested, reviewed or unresolved.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Inbound event ID

An inbound event ID identifies delivery of the same intended work. Repeated receipt should not create duplicate queue items, but every delivery can remain visible in an audit. A reused ID with changed content is a conflict, not an ordinary duplicate. Scope keys by source/owner in a real multi-tenant service.

## Step 2 · Correction history

Correction history records old and new values alongside the resulting version. Updating only the current topic loses why an item moved queues. Write correction and state change transactionally, then reject stale review versions. The baseline stores one correction and proves an older reviewer cannot overwrite it.

## Step 3 · Queue state

Queue state separates receipt from successful classification. Save unresolved work before calling an unreliable classifier, so provider failure does not drop the message. Reopen storage to prove retention. A file-backed fixture demonstrates local persistence but not authenticated HTTP access or concurrent reviewer behavior; add those boundaries in the integrated app.

```python
import sqlite3
from tempfile import TemporaryDirectory
from pathlib import Path
with TemporaryDirectory() as folder:
    path=Path(folder)/'queue.sqlite'; db=sqlite3.connect(path)
    db.executescript('CREATE TABLE items(id TEXT PRIMARY KEY, message TEXT, topic TEXT, version INT); CREATE TABLE deliveries(id TEXT); CREATE TABLE corrections(id TEXT, old TEXT, new TEXT);')
    def receive(identifier,message):
        with db:
            db.execute('INSERT INTO deliveries VALUES(?)',(identifier,))
            db.execute("INSERT OR IGNORE INTO items VALUES(?,?,?,1)",(identifier,message,'unresolved'))
    receive('t4','charged twice'); receive('t4','charged twice')
    def correct(identifier,version,topic):
        with db:
            old=db.execute('SELECT topic FROM items WHERE id=? AND version=?',(identifier,version)).fetchone()
            if old is None: return 'conflict'
            changed=db.execute('UPDATE items SET topic=?,version=version+1 WHERE id=? AND version=?',(topic,identifier,version)).rowcount
            if changed!=1: return 'conflict'
            db.execute('INSERT INTO corrections VALUES(?,?,?)',(identifier,old[0],topic))
        return 'saved'
    assert correct('t4',1,'billing')=='saved' and correct('t4',1,'technical')=='conflict'
    db.close(); db=sqlite3.connect(path)
    assert db.execute('SELECT count(*) FROM items').fetchone()[0]==1
    assert db.execute('SELECT count(*) FROM deliveries').fetchone()[0]==2
    assert db.execute('SELECT old,new FROM corrections').fetchone()==('unresolved','billing')
    db.close()
print('two deliveries, one durable work item, one correction; stale review blocked')
```

## Walk through the mechanism and its limits

Receipt and classification are separated: inputs enter unresolved even when a classifier is unavailable. Every delivery is recorded, while a stable input ID deduplicates work. The transaction records correction history alongside the current state. This single-reviewer prototype has no user authentication; add reviewer scope before exposing it over HTTP. A reused event ID with different content also requires explicit conflict handling.
