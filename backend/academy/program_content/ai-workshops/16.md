## Before you begin

## Why this decision matters

A useful app sprint packages a narrow workflow so another person can use it. Pick one of the first five studios and define the smallest complete path from input to saved output and review. Avoid combining every project into one interface. A practical scope includes errors, an empty state, and a known limitation.

Use the artifacts you built in the preceding studios as your implementation foundation. Your sprint owns its input schema, review workflow, evaluation fixtures, user-facing behavior and acceptance criteria. Choose a small interface and a local durable store, then prove one complete path before adding integrations.

## Vocabulary used in this session

### Release scope

The smallest complete user path and the explicit capabilities left outside it.

### Acceptance scenario

A concrete input and observable result that demonstrates a requirement.

### Dependency boundary

A clear distinction between real, fake and manual components.

## Worked implementation: Scope a useful end-to-end application

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
scenarios=[
 {'id':'normal','path':['input','draft','review','save','export']},
 {'id':'missing','path':['input','needs_review','save']},
 {'id':'failure','path':['input','generation_failed','retry']},
 {'id':'reload','path':['read_saved','show_reviewed_version']},
 {'id':'other_owner','path':['authenticate','deny_read']},
]
included={'text_input','draft_table','revision_save','reviewed_csv'}
excluded={'live_recording','calendar_send','OCR'}
assert not (included & excluded)
assert len({s['id'] for s in scenarios})==5
assert any('generation_failed' in s['path'] for s in scenarios)
print({'selected':'meeting action register','scenarios':[s['id'] for s in scenarios],
       'manual':'transcript annotation','fake':'extraction adapter','real':'local save and CSV'})
```

```text
{'selected': 'meeting action register', 'scenarios': ['normal', 'missing', 'failure', 'reload', 'other_owner'], 'manual': 'transcript annotation', 'fake': 'extraction adapter', 'real': 'local save and CSV'}
```

## Walk through the mechanism and its limits

The scope names a complete student-visible path and five acceptance scenarios. Dependency labels identify what is manually annotated, fake, or actually implemented; they prevent a prototype from masquerading as live transcription. Listing scenarios is planning evidence, not proof they passed. The next session must collect observations through the actual UI and server.
