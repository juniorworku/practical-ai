## Understand the decision: Scope a useful end-to-end application

## Before you begin

## Why this decision matters

A useful app sprint packages a narrow workflow so another person can use it. Pick one of the first five studios and define the smallest complete path from input to saved output and review. Avoid combining every project into one interface. A practical scope includes errors, an empty state, and a known limitation.

Use the artifacts you built in the preceding studios as your implementation foundation. Your sprint owns its input schema, review workflow, evaluation fixtures, user-facing behavior and acceptance criteria. Choose a small interface and a local durable store, then prove one complete path before adding integrations.

## Vocabulary used in this session

### Release scope

The smallest complete user path and the explicit capabilities left outside it.

### Acceptance scenario

A concrete input and observable result that demonstrates a requirement.

### Dependency boundary

A clear distinction between real, fake and manual components.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Release scope

Release scope selects a useful connected path and explicitly excludes costly distractions. The meeting register slice covers input, draft, review, save and export plus failures. A feature earns its place by improving a named scenario. Live recording can remain deferred while text-to-reviewed-register is made reliable.

## Step 2 · Acceptance scenario

An acceptance scenario specifies actor, fixture/revision, starting state, action and observable result. “Test saving” is incomplete: say what is saved, who can read it and what survives reload. Planning a scenario is not passing it. Keep expected result and actual observation in separate fields until the integrated application is exercised.

## Step 3 · Dependency boundary

A dependency boundary says which stage is manual, fake or real. The fixture’s annotations are manual, extraction adapter fake and local persistence real. That honest split lets students test orchestration without claiming live transcription or model accuracy. Replacing a fake later requires evaluation of the new boundary, not inheriting its assumed correctness.

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Graduation builds toward operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. Early checkpoints assess only boundaries already taught; future deployment controls are planned rather than claimed complete. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to one integrated studio app

### Latency vs. Cost vs. Quality

Load-test offered vs. completed work, p95 and cost per accepted result at stated concurrency. Autoscaling settings are hypotheses until observed against downstream/GPU limits.

### Deterministic Evaluation

Test readiness against the actual database, restart/readback, isolated restore, denied owner access, overload rejection and a dependency outage on the deployed revision.

### Context Management

Budget resident model memory/KV cache and per-request context separately. Keep tenant/revision-aware application caches; never assume a process-local cache is shared across replicas.

## Failure and deployment work

Separate request concurrency, worker capacity and model/GPU capacity. Add admission control, shared quotas, bounded queues, maximum instances and a documented fallback/stop budget.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
