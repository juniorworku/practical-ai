## Why this decision matters

Integration often fails where individually correct pieces disagree: field names, status codes, owner IDs, or revision semantics. Trace one input through the browser, API, database, and response. Use actual observed requests and saved records to locate the broken boundary.

Keep synthetic fixtures and test accounts separate from real data. A browser test that only checks a heading does not prove persistence. Save a meaningful value, reload, sign out and back in, and verify that it is still present for the correct owner. Then attempt the same read as another user. This is the minimum useful evidence for a multi-user workflow.

## Vocabulary used in this session

### Integration boundary

A handoff such as browser-to-API or API-to-database where contracts must agree.

### Durable readback

Retrieving saved server state after reload or restart.

### Account isolation

A user cannot access another owner’s records even with a known record ID.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Integration boundary

An integration boundary connects browser state, HTTP request, server validation and database write. A screen updating optimistically is not a completed save. Carry authenticated owner and expected revision on the server, handle invalid/stale requests, and expose a response the browser can interpret without discarding unsaved edits.

## Step 2 · Durable readback

Durable readback proves stored data survives the relevant boundary: reload, process replacement or restore. The SQLite fixture closes and reopens its connection to inspect a corrected due date. This is stronger than a local UI variable but still does not exercise HTTP, browser error handling or service restart. Collect those separately in the application.

## Step 3 · Account isolation

Account isolation requires owner scope on both writes and reads. A hidden row in the UI is insufficient if its API ID can be requested directly. Return a documented inaccessible outcome without leaking another account’s content. A stale own-record edit is a different conflict and should preserve the user’s correction for comparison.

## Predict before running

Read the assertions and predict the output and rejected cases. Save the **entire** following block as `example.py` in a new scratch folder. Use Python 3.12; every import and synthetic fixture required for this example is included. Run `python3 -I example.py`. Assertions must be enabled; do not use `-O`. No model, network, database service or third-party package is required. SQLite examples create a temporary database and clean it up.

```python
import sqlite3
from tempfile import TemporaryDirectory
from pathlib import Path
with TemporaryDirectory() as folder:
    path=Path(folder)/'actions.sqlite'; db=sqlite3.connect(path)
    db.execute('CREATE TABLE actions(id TEXT PRIMARY KEY,owner TEXT,due TEXT,version INT)')
    with db: db.execute('INSERT INTO actions VALUES(?,?,?,?)',('a2','acme','2026-10-23',2))
    def save(actor, expected, due):
        with db:
            changed=db.execute('UPDATE actions SET due=?,version=version+1 WHERE id=? AND owner=? AND version=?',(due,'a2',actor,expected)).rowcount
        return 200 if changed else 409
    assert save('acme',2,'2026-10-24')==200
    assert save('acme',2,'2026-10-25')==409
    db.close(); db=sqlite3.connect(path)
    assert db.execute('SELECT due,version FROM actions WHERE id=? AND owner=?',('a2','acme')).fetchone()==('2026-10-24',3)
    assert db.execute('SELECT due FROM actions WHERE id=? AND owner=?',('a2','other')).fetchone() is None
    db.close()
print('durable due-date correction; stale save rejected; cross-owner read absent')
```

## Walk through the mechanism and its limits

The store contract connects scoped identity, revision-aware write and durable readback. Reopening the database is stronger than reading a React variable, but still does not test HTTP or a browser. The 409 return is an application simulation; your real API must distinguish inaccessible IDs without leaking existence and convert true stale edits into a documented conflict response.

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Completion requires operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to one integrated studio app

### Latency vs. Cost vs. Quality

Load-test offered vs. completed work, p95 and cost per accepted result at stated concurrency. Autoscaling settings are hypotheses until observed against downstream/GPU limits.

### Deterministic Evaluation

Test readiness against the actual database, restart/readback, isolated restore, denied owner access, overload rejection and a dependency outage on the deployed revision.

### Context Management

Budget resident model memory/KV cache and per-request context separately. Keep tenant/revision-aware application caches; never assume a process-local cache is shared across replicas.

## Failure and deployment work

Separate request concurrency, worker capacity and model/GPU capacity. Add admission control, shared quotas, bounded queues, maximum instances and a documented fallback/stop budget.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
