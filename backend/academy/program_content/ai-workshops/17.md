# Integrate, persist, and test the workflow

## The engineering or business decision

Integration often fails where individually correct pieces disagree: field names, status codes, owner IDs, or revision semantics. Trace one input through the browser, API, database, and response. Use actual observed requests and saved records to locate the broken boundary.

Keep synthetic fixtures and test accounts separate from real data. A browser test that only checks a heading does not prove persistence. Save a meaningful value, reload, sign out and back in, and verify that it is still present for the correct owner. Then attempt the same read as another user. This is the minimum useful evidence for a multi-user workflow.

## Worked example

The action register saves a confirmed due date. After refresh, the date returns from the server rather than a browser variable. A second account cannot fetch the record ID. A failed export preserves the confirmed register for retry.

## Build it yourself

1. Connect the smallest interface to an API and durable store.
2. Run all five acceptance scenarios through the real UI.
3. Check saved state after reload and service restart.
4. Test cross-user reads and a dependency failure, preserving observations in an evidence log.

## Break it deliberately

Stop the API after the form is submitted. Confirm that the UI shows an error and preserves input instead of displaying a false saved state.

## Acceptance checks

- The browser reads saved server state after restart.
- Unauthorized users cannot read another account’s records.
- A failure case is tested across the real integration boundary.
