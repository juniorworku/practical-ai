# Write a statement of work with acceptance tests

## Understand the decision: Write a statement of work with acceptance tests

## Before you begin

Bring your artifacts from sessions 1–4 of this program. Continue the same fictional training-provider engagement and keep assumption labels and revision IDs intact.

## Why this decision matters

A statement of work translates a proposal into testable responsibilities. Include scope, deliverables, milestones, required client inputs, review windows, acceptance method, and a change process. This program uses a planning template; actual contractual and legal terms need the appropriate local review before use.

Acceptance should describe observable behavior on a named dataset and environment. “Works well” is not a useful condition. Agree on which failures block acceptance and which are documented limitations. Identify who is authorized to accept the work and what happens when client data or access arrives late.

## Vocabulary used in this session

### Statement of work

A planning document defining deliverables, responsibilities, dependencies and acceptance.

### Acceptance condition

An agreed observable behavior on a named dataset and environment.

### Change request

A documented proposal to alter scope with its cost, schedule and test impacts.

## Statements of work as executable acceptance

### Translate outcomes into observable behavior
A scope document should connect every deliverable to an acceptance scenario. “Accurate AI summaries” is not testable. “For each approved note, the draft links every factual objective to a source section; missing objectives are flagged for review” identifies behavior a reviewer can inspect. Add negative cases as well as the normal path. Treat this as a delivery planning exercise; real contractual language requires context-specific review.

### Use given, when, then, evidence
Write: Given a named dataset and role, when an action occurs, then an observable result follows, proven by an artifact. Example: Given note N03 with no objective, when a reviewer creates a draft, then the objective is marked missing and export is blocked until reviewed; evidence is the saved draft revision and review event. Include environment and dataset revisions so the test can be repeated.

### Define status categories
Use passed, failed, not tested, and deferred. A deferred condition needs an owner, reason, risk, and explicit acceptance decision. “We did not see a problem” is not equivalent to passed. A demo using one known good document cannot establish behavior on missing fields or failed provider calls. Keep screenshots as supporting evidence rather than the entire test record.

### Define the change boundary
A request to support scanned PDFs changes ingestion, OCR quality, evaluation data, latency, and probably hosting. It is a scope change even when the interface still shows an upload box. The change process should identify affected requirements, effort, acceptance tests, and decision owner. Preserve the original agreement until the change is explicitly accepted.

### Include operational acceptance
Add client-owned accounts, backup/restore, reviewer permissions, and fallback operation where appropriate. A feature can pass its happy path while remaining impossible for the client to operate. Tie handover and access removal to acceptance, not to an informal promise after the project ends.

### Acceptance exercise
Create eight scenarios: normal note, missing objective, contradictory source, malformed input, duplicate submission, unauthorized reviewer, provider failure, and stale edit. Assign each to an owner and an evidence file. Have a peer challenge one ambiguous condition and rewrite it until both of you would give the same result on the same input.

## Critique and transfer

Complete eight scenarios and assign a reviewer and evidence path to each. Rewrite one ambiguous “good quality” criterion until two peers agree how to judge the same output.

Treat the completed specimen as a model of reasoning, not a result to copy into your own evidence. Your submission must replace its assumptions and statuses with your own observations, or remain explicitly simulated.

## Worked example

Acceptance scenario: “Given ten approved synthetic notes, the prototype produces ten draft handouts, each linked to its source note. Missing learning objectives are flagged, not invented. The instructor can edit and export a draft. No output is sent externally.” The dataset revision and evaluation environment are part of the scenario.

## Build it yourself

1. Draft a statement of work with a deliverables table and milestone owners.
2. Write eight acceptance scenarios including missing data, malformed input, unauthorized access, and provider failure.
3. Specify client dependencies and a review/feedback process.
4. Add a change-request template that records cost, schedule, and acceptance impacts.

## Break it deliberately

The client supplies a new document type at the final review. Evaluate it as a scope change rather than silently weakening acceptance tests.

## Acceptance checks

- Acceptance scenarios name inputs and observable outcomes.
- Responsibilities and dependencies have owners.
- A scope change has a documented review path.
