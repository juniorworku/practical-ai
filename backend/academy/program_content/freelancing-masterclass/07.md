## Understand the decision: Map data, access, and retention

## Before you begin

## Why this decision matters

Data access is a delivery dependency and a trust boundary. Inventory what data the workflow reads, where it is stored, who can see it, whether it is sent to a provider, and when it is deleted. Obtain the client’s authorization for the specific flow before using real information. A client sharing one sample does not authorize uploading the entire archive.

Start with synthetic fixtures and a minimal data schema. Avoid including credentials or personal content in demonstrations, logs, screenshots, or portfolio artifacts. Document the account owner for each external service and how access will be revoked at handover. Use separate client environments rather than mixing data in a personal experiment.

## Vocabulary used in this session

### Data-flow map

A record of inputs, destinations, processing, storage, logs and exports.

### Data minimization

Using only the fields needed for the agreed task.

### Access revocation

Removing implementer privileges while preserving client-owned operation.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Data-flow map

A data-flow map follows each field from intake through storage, provider calls, logs, exports and backups. A new hosted model is a new destination even if the interface looks unchanged. Name the role with access and purpose at each stage. Track configuration names rather than secret values in the handover document.

## Step 2 · Data minimization

Data minimization excludes fields unnecessary for the bounded task. Learner names are outside this handout pilot, so reject or remove them before processing. Hiding them in the interface does not remove them from uploaded files or logs. Use a synthetic marker to inspect actual stored/exported payloads at each boundary.

## Step 3 · Access revocation

Access revocation changes who can use data but does not automatically delete every copy. Exports and backups have separate retention/expiry policies and owners. Record those policies as agreements to obtain, not universal defaults. A revoked implementer should lose access without disabling the client’s separate service identity or recovery role.

## Data inventory and least-privilege delivery

### Map data by movement
Inventory the fields needed for each step, where they originate, which component reads them, whether a provider receives them, where outputs are stored, and when they are removed. Include logs, caches, backups, and exports. “We delete the uploaded file” is incomplete if its content remains in traces or generated drafts. Begin with synthetic notes so you can test the data flow without real client information.

### Separate account ownership from implementer access
The client should be able to operate the service after your access is removed. Use client-owned service accounts and narrowly scoped implementer roles for the exercise. Record who can rotate keys, change billing, approve users, and recover backups. Do not put actual keys in a handover document or a screenshot. Document variable names and storage locations instead.

### Apply least privilege to behavior
A drafting service needs read access to approved notes and write access to draft storage. It does not need permission to send email or change the source curriculum. Separate reviewer approval from generation. Log who approved which revision and invalidate approval when the material changes. A model’s instruction cannot substitute for an application permission check.

### Build retention into the design
For each data class, specify purpose, access, retention trigger, and deletion method. Test deletion in primary storage and explain how backup retention affects complete removal. If jurisdiction-specific obligations matter, investigate them before a real engagement; this lesson provides a technical inventory, not a universal legal rule.

### Trace one record
Follow synthetic note N03 through ingestion, draft generation, review, export, logging, and backup. At each boundary, list the minimum fields. Replace full source text in operational logs with IDs and status where possible. Confirm that error messages do not echo credentials or confidential payloads.

### Access exercise
Create an operator, reviewer, administrator, and implementer role. Write an allow/deny matrix and test one allowed and one denied action per role. Remove implementer access and verify routine operation still works. The evidence should describe the actual denial or success, not merely a checkbox saying security was considered.

|---|---|---|---|---|
| Approved note text | local store | instructor | pilot plus 30 days, to agree | delete then read returns absent |

The offline fake provider receives no real client data. A later hosted model adds a destination and must trigger a new data-flow decision. The retention values are planning assumptions, not default policy or compliance claims.

Deleting an input does not delete an already exported handout or every backup. Record those separate lifecycles and the owner responsible for each. A hidden sheet in a supplied workbook must be inspected before intake, not discovered after upload.

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Graduation builds toward operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. Early checkpoints assess only boundaries already taught; future deployment controls are planned rather than claimed complete. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to a permissioned client-data inventory and prototype

### Latency vs. Cost vs. Quality

Compare a manual baseline with the prototype on identical synthetic inputs, reporting elapsed/review time, total attempts and accepted outputs.

### Deterministic Evaluation

Use a reviewed acceptance set with missing data and unsupported-claim cases; no polished demo substitutes for the failure report.

### Context Management

Build a source/permission manifest with digest/revision, token estimate, omitted fields and cache invalidation rules before any provider request.

## Failure and deployment work

Assign rate/budget caps, failure/manual fallback, hosting ownership, review duties, restore evidence and escalation before expanding the service.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
