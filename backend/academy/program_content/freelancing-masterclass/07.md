# Map data, access, and retention

## The engineering or business decision

Data access is a delivery dependency and a trust boundary. Inventory what data the workflow reads, where it is stored, who can see it, whether it is sent to a provider, and when it is deleted. Obtain the client’s authorization for the specific flow before using real information. A client sharing one sample does not authorize uploading the entire archive.

Start with synthetic fixtures and a minimal data schema. Avoid including credentials or personal content in demonstrations, logs, screenshots, or portfolio artifacts. Document the account owner for each external service and how access will be revoked at handover. Use separate client environments rather than mixing data in a personal experiment.

## Worked example

The handout workflow reads approved course notes and outputs drafts for instructors. Learner names are unnecessary and should be excluded. A provider integration would introduce another data destination; the client must understand and approve that choice before real notes leave the agreed environment.

## Build it yourself

1. Create a data-flow diagram covering input, processing, provider boundary, storage, logs, and exports.
2. List data fields, owners, access roles, retention, and deletion behavior.
3. Build synthetic samples that exercise the same structure without private content.
4. Write a checklist for access provisioning and revocation.

## Break it deliberately

A sample contains a hidden sheet with learner names. Your intake process should inspect and minimize the sample before it reaches any provider.

## Acceptance checks

- Every data destination and account owner is listed.
- Only necessary fields appear in the prototype.
- Access removal and deletion are part of the handover plan.
