## Understand the decision: Build a thin pilot with visible limitations

## Why this decision matters

A pilot tests whether the workflow can meet the agreed outcome within constraints. Implement a narrow end-to-end path rather than a broad collection of mock screens. Use fake adapters to test behavior and a real integration only when it is necessary and authorized. Label each simulated step clearly in the demo.

Build uncertainty handling before polishing presentation. Missing source content, provider failure, and invalid output should produce a reviewable state without losing user work. The pilot should help the client make a go/no-go decision; it should not conceal manual steps behind an “AI automation” label.

## Vocabulary used in this session

### Thin pilot

A narrow but complete end-to-end workflow that tests an agreed uncertainty.

### Fake integration

A clearly labeled deterministic substitute for an external dependency.

### Go/no-go evidence

Observed results that support continuing, conditioning or stopping an engagement.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Thin pilot

A thin pilot implements the smallest connected path needed to test the client decision. Read one authorized note, produce a draft, flag missing information, save/reload and review before export. A polished mockup alone cannot show recoverable state or measured review effort. Keep the manual workflow available as fallback.

## Step 2 · Fake integration

A fake integration supplies controlled outputs or failures to isolate orchestration. It is valuable when named honestly. The reference generator below is deterministic, not an AI model; it tests missing-objective and timeout handling. It cannot establish the quality or safety of a future model’s teaching content.

## Step 3 · Go/no-go evidence

Go/no-go evidence comes from the declared scenarios and thresholds. Keep normal, missing-objective and timeout results, including original input and status. A demo viewer should identify every fake/manual component without coaching. Do not infer time savings, readiness or permission for automatic distribution from a successful synthetic path.

## Prototype, pilot, and production evidence

### Match the build to the question
A prototype can test whether users understand a review screen using fake data. A pilot tests a bounded workflow with representative inputs and real operating constraints. Production serves ongoing work with assigned ownership and recovery. Label the stage clearly. A polished interface does not turn a prototype into production, and a local demo does not establish reliable multi-user operation.

### Build one vertical slice
For the handout service, implement source input → draft creation → instructor review → saved approved revision → export. A collection of disconnected screens cannot test the end-to-end handoff. Keep the slice small: one input template, one reviewer role, one output format. Preserve the manual fallback so the team can finish work if the pilot stops.

### Show uncertainty in the interface
Missing source information should appear as unresolved, not a confident completion. Display draft status, source revision, review state, and provider failure separately. A disabled export with a clear reason is more useful than silently producing an incomplete file. The interface should help a reviewer understand what requires judgment.

### Define what each evidence type proves
A screenshot proves appearance at a moment. An API response proves one request returned a value. A reload check can show persistence. A second-user denial shows one access boundary. A restore rehearsal demonstrates a recovery procedure in the tested environment. Combine evidence to support the claim you actually make; do not use a screenshot to claim database isolation.

### Add a stop rule
Choose a condition that pauses expansion: missing source ownership, unacceptable false acceptance, review time above the baseline, or no one available to operate the service. Agree on the rule before looking at favorable outputs. A failed pilot can still be a useful engagement when it prevents an expensive unsupported rollout.

### Pilot exercise
Write the decision question, smallest complete flow, representative cases, success measure, guardrail, fallback, and expansion gate. Implement the slice with synthetic data. Ask a reviewer to handle one unseen normal case and one failure without coaching. Record where the design failed to communicate its limits.

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Graduation builds toward operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. Early checkpoints assess only boundaries already taught; future deployment controls are planned rather than claimed complete. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to a permissioned client-data inventory and prototype

### Latency vs. Cost vs. Quality

Compare a manual baseline with the prototype on identical synthetic inputs, reporting elapsed/review time, total attempts and accepted outputs.

### Deterministic Evaluation

Use a reviewed acceptance set with missing data and unsupported-claim cases; no polished demo substitutes for the failure report.

### Context Management

Build a source/permission manifest with digest/revision, token estimate, omitted fields and cache invalidation rules before any provider request.

## Failure and deployment work

Assign rate/budget caps, failure/manual fallback, hosting ownership, review duties, restore evidence and escalation before expanding the service.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
