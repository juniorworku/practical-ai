# Build a thin pilot with visible limitations

## Prototype, pilot, and production evidence

### Match the build to the question
A prototype can test whether users understand a review screen using fake data. A pilot tests a bounded workflow with representative inputs and real operating constraints. Production serves ongoing work with assigned ownership and recovery. Label the stage clearly. A polished interface does not turn a prototype into production, and a local demo does not establish reliable multi-user operation.

### Build one vertical slice
For the handout service, implement source input → draft creation → instructor review → saved approved revision → export. A collection of disconnected screens cannot test the end-to-end handoff. Keep the slice small: one input template, one reviewer role, one output format. Preserve the manual fallback so the team can finish work if the pilot stops.

### Show uncertainty in the interface
Missing source information should appear as unresolved, not a confident completion. Display draft status, source revision, review state, and provider failure separately. A disabled export with a clear reason is more useful than silently producing an incomplete file. The interface should help a reviewer understand what requires judgment.

### Define what each evidence type proves
A screenshot proves appearance at a moment. An API response proves one request returned a value. A reload check can show persistence. A second-user denial shows one access boundary. A restore rehearsal demonstrates a recovery procedure in the tested environment. Combine evidence to support the claim you actually make; do not use a screenshot to claim database isolation.

### Add a stop rule
Choose a condition that pauses expansion: missing source ownership, unacceptable false acceptance, review time above the baseline, or no one available to operate the service. Agree on the rule before looking at favorable outputs. A failed pilot can still be a useful engagement when it prevents an expensive unsupported rollout.

### Pilot exercise
Write the decision question, smallest complete flow, representative cases, success measure, guardrail, fallback, and expansion gate. Implement the slice with synthetic data. Ask a reviewer to handle one unseen normal case and one failure without coaching. Record where the design failed to communicate its limits.

## Choose the Smallest Slice That Can Change the Decision

## Vertical Means Evidence End to End

A useful slice crosses the minimum real workflow needed to observe an outcome. It can be narrow in users, data, duration, and capability. It should not be narrow by removing the exact uncertainty you need to test.

Examples:

- A read-only replay across ten real incidents tests service identification and operator trust.
- A polished dashboard on synthetic data may test comprehension but not data feasibility.
- A production auto-remediator tests everything at once with unacceptable consequence.

## Define Required Proof First

Take the highest-risk open assumptions and turn them into a required proof set. A candidate slice is eligible only if it covers that set.

Then compare eligible slices on:

| Dimension | Direction |
|---|---|
| Outcome value | More is better |
| Uncertainty reduced | More is better |
| Effort | Less is better |
| Consequence | Less is better |
| Reversibility | More is better |

The lab’s score is intentionally simple. The eligibility gate matters more than the arithmetic.

**System flow**

- Required proof → Candidate slice 1
- Candidate slice 2
- Candidate slice 3
- Reject
- Compare evidence per effort and risk
- Build one slice

## Common False Minimums

- **The UI-only minimum:** removes the data and operational uncertainty.
- **The infrastructure-only minimum:** proves technical possibility without user value.
- **The happy-path minimum:** omits the exception that creates most risk.
- **The demo minimum:** produces a persuasive artifact but no repeatable measurement.
- **The platform minimum:** builds reusable machinery before one workflow earns it.

## Add a Stop Rule

Before implementation, write what happens if the slice fails:

- abandon the outcome;
- change the target user or situation;
- test a different mechanism;
- collect better evidence;
- narrow authority further.

If every result leads to “keep building,” the slice is not an experiment.

## Choose Prototype, Pilot, or Production Deliberately

## Three Different Questions

| Stage | Primary question |
|---|---|
| Prototype | Can this mechanism produce the evidence at all? |
| Pilot | Does it work safely with a bounded real audience and real conditions? |
| Production | Can we own it continuously at the promised reliability and risk level? |

A prototype can be technically complete and still be disposable. A pilot can use production data while remaining limited in audience and authority. Production begins when the organization accepts ongoing responsibility.

## Prototype

Use a prototype when the unknown does not require real users or real data. Keep it:

- discardable;
- isolated;
- narrow in behavior;
- explicit about the learning question;
- free of false operational guarantees.

Do not optimize architecture before the mechanism earns another stage.

## Pilot

Use a pilot when the unknown requires real behavior, realistic data, or a real workflow, but consequence or readiness is not yet compatible with broad release.

A pilot needs:

- a named audience;
- a human owner;
- bounded duration and authority;
- audit and rollback;
- outcome and guardrail thresholds;
- exit criteria for expand, revise, or stop.

## Production

Production needs more than deployment:

- service level objective;
- on-call and incident ownership;
- security and privacy review;
- cost and capacity controls;
- rollback and recovery;
- continuous monitoring;
- a retirement path.

**System flow**

- Unknown
- Prototype
- Pilot
- Production

## Stage Drift

Prototype code becomes dangerous when it acquires users, data, or authority without acquiring ownership. Mark prototype and pilot boundaries in configuration, access control, telemetry, and documentation. A warning banner is not enough.

The stage should be observable from the system itself.

## Apply it: Build a thin pilot with visible limitations

## The engineering or business decision

A pilot tests whether the workflow can meet the agreed outcome within constraints. Implement a narrow end-to-end path rather than a broad collection of mock screens. Use fake adapters to test behavior and a real integration only when it is necessary and authorized. Label each simulated step clearly in the demo.

Build uncertainty handling before polishing presentation. Missing source content, provider failure, and invalid output should produce a reviewable state without losing user work. The pilot should help the client make a go/no-go decision; it should not conceal manual steps behind an “AI automation” label.

## Worked example

The handout pilot accepts one approved text note, drafts a section outline, checks required headings, saves a draft, and exports after review. The provider is fake in the offline baseline. An instructor performs a manual factual check, which remains visible in the process map.

## Build it yourself

1. Choose one acceptance scenario and implement the complete vertical slice.
2. Add a second path for missing information and a third for dependency failure.
3. Keep draft input and saved work intact across a failed generation step.
4. Record a demo that names real, fake, and manual components.

## Break it deliberately

The source note lacks an important concept. The pilot must flag the omission rather than filling it with plausible unsupported teaching content.

## Acceptance checks

- The pilot implements a complete agreed scenario.
- Known limitations are visible to the reviewer.
- A failure leaves the client’s input recoverable.
