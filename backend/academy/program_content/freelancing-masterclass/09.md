# Use client feedback without losing scope

## Understand the decision: Use client feedback without losing scope

## Before you begin

Bring your artifacts from sessions 1–8 of this program. Continue the same fictional training-provider engagement and keep assumption labels and revision IDs intact.

## Why this decision matters

Feedback contains bugs, preferences, new requirements, and misunderstandings. Classify it before acting. A bug violates an agreed acceptance condition; a preference changes presentation; a new requirement adds behavior or constraints. Record each item with an example and its effect on the user task.

Do not defend every design choice or accept every request immediately. Reproduce the issue, identify the responsible layer, and compare it with the scope. A change decision should include an impact on quality, effort, schedule, and tests. Maintain an evidence trail so review conversations refer to a specific version rather than different memories of a demo.

## Vocabulary used in this session

### Defect

A behavior that violates an agreed acceptance condition.

### Preference

A requested presentation change judged against the audience and rubric.

### New requirement

Additional behavior or constraints outside the agreed scope.

## Learn each concept step by step

Work through these explanations before the completed example or exercise. Follow the inputs, mechanism and decision boundary rather than memorizing the definitions.

## Step 1 · Defect

A defect violates an existing acceptance condition. Reproduce it on the named release and fixture before estimating a fix. Losing an approved objective on export is a defect against the promised template; restoring it does not require inventing a new service package. Preserve failing and corrected observations.

## Step 2 · Preference

A preference changes presentation within the agreed task and still needs an audience reason. “Too formal” is not automatically a bug or an excuse to ignore the user. Compare two revisions on the instructor’s task and rubric, then record a decision. Avoid endless tone changes with no stopping criterion.

## Step 3 · New requirement

A new requirement changes capability, authority, input format or operational scope. Translation adds datasets and review needs; allowing assistants to approve changes permissions even if it is one dropdown. Classify by the promise and consequence rather than implementation size. Keep deferred work with an owner and reconsideration condition.

## Feedback triage and bounded iteration

### Treat feedback as evidence about a layer
Separate a source defect, model error, interface confusion, missing capability, and changed business objective. Each has a different owner and remedy. “The draft is wrong” might come from contradictory approved notes; a prompt tweak could hide the problem. Ask for the input, observed output, expected behavior, and consequence before choosing a fix.

### Use a triage record
Store ID, case revision, reporter role, observation, expected behavior, severity, owning layer, proposed action, and closure evidence. Link the record to an acceptance scenario if one exists. If the requested behavior falls outside the agreed scope, record it as a change candidate rather than silently absorbing it into defect work.

### Prioritize using consequence and reproducibility
A reproducible source-citation failure can block the pilot even if it appears rarely. A cosmetic request may be frequent but have little effect on acceptance. Use severity, exposure, and reversibility, and keep uncertainty visible. Avoid multiplying arbitrary scores into a false impression of precision.

### Close the learning loop
For each accepted fix, add a regression case, update the owning rule or component, and define when to recheck it. A fix is not closed merely because the developer changed something. The original reporter or an authorized reviewer should be able to repeat the case and observe the intended behavior.

### Retire stale controls
If a workaround no longer applies after a source or product change, give someone responsibility for removing it. Accumulated prompt instructions can conflict and become impossible to audit. Keep a reason and review date for temporary controls. Prefer a small testable rule over an ever-growing prompt warning.

### Feedback exercise
Create five feedback records covering source error, unclear review label, unsupported scan, duplicate job, and a new email feature. Classify defect versus change, assign an owner, and write the evidence needed for closure. Implement one simulated correction and rerun its failing case plus the existing representative set.

## Apply the three engineering pillars

## Software-first practice

Build interfaces, asynchronous services, API adapters and recoverable data flows before studying algorithm derivations. Use mathematics to explain a measured engineering decision.

## Production evidence

A notebook or chat demo is an early prototype. Completion requires operational evidence: deployment/readiness, bounded work, rate limits, error recovery and persisted state. The 10% framing is a teaching heuristic, not a measured universal percentage.

## Apply the three pillars to a permissioned client-data inventory and prototype

### Latency vs. Cost vs. Quality

Compare a manual baseline with the prototype on identical synthetic inputs, reporting elapsed/review time, total attempts and accepted outputs.

### Deterministic Evaluation

Use a reviewed acceptance set with missing data and unsupported-claim cases; no polished demo substitutes for the failure report.

### Context Management

Build a source/permission manifest with digest/revision, token estimate, omitted fields and cache invalidation rules before any provider request.

## Failure and deployment work

Assign rate/budget caps, failure/manual fallback, hosting ownership, review duties, restore evidence and escalation before expanding the service.

## Evaluation precision

Automate repeatable checks with fixed inputs and versioned expectations. Model judges, faithfulness scores and semantic reviews can be stochastic; record judge/configuration versions and disagreement rather than calling them deterministic truth.
