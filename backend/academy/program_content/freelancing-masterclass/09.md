# Use client feedback without losing scope

## The engineering or business decision

Feedback contains bugs, preferences, new requirements, and misunderstandings. Classify it before acting. A bug violates an agreed acceptance condition; a preference changes presentation; a new requirement adds behavior or constraints. Record each item with an example and its effect on the user task.

Do not defend every design choice or accept every request immediately. Reproduce the issue, identify the responsible layer, and compare it with the scope. A change decision should include an impact on quality, effort, schedule, and tests. Maintain an evidence trail so review conversations refer to a specific version rather than different memories of a demo.

## Worked example

“The export is missing the approved learning objectives” is a defect if the statement of work requires them. “Also translate all handouts into three languages” is a new requirement. “This paragraph is too formal” is a preference to test against the agreed audience and rubric.

## Build it yourself

1. Collect ten role-play feedback items and classify each.
2. Reproduce two defects with fixtures and add regression tests.
3. Write one change request for a genuine expansion.
4. Send no external messages; prepare a local decision log and revised milestone plan for review.

## Break it deliberately

A late preference conflicts with an earlier approved requirement. Document the conflict and obtain a scope decision before implementing it in the simulated engagement.

## Acceptance checks

- Feedback refers to examples and a version.
- Defects and new scope have different handling.
- Each accepted change updates relevant acceptance checks.

## Deliverable

Save **`client-03/feedback-decision-log.md`** in your separate program workspace. Include your inputs, actual outputs, decisions, and unresolved limitations. Budget about **120 minutes** for reading, implementation and review; this is an estimate, not a timed requirement.
